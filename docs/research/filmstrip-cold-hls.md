# Filmstrip: холодный HLS и трафик

Проверено 15 ноября 2026 года. Решение и время жизни кеша:
[ADR 0011](../adr/0011-photo-viewer-stack.md).

## Вывод для продукта

Холодный HLS отклонён как основной источник кадров: экономия трафика не
компенсирует задержку первого кадра и готовности длинной ленты. Рабочий путь:
local → original → низкий фиксированный HLS только при неподдерживаемом формате
original. Сетевые ошибки и тайм-ауты не запускают transcode. Первое открытие
читаемого original не делает discovery; кеш в памяти viewer и независимость
от playback quality уменьшают повторные извлечения.

## Метод

Таблица ниже получена при проверке экспериментальной политики HLS-first:
production extraction без playback, сначала `RemoteVideoFrames` на `/stream`,
затем низкий HLS через прежний `VideoFramesFactory` с новым VOD client id
на том же файле. Baseline не подготавливал HLS; готовые bitmap не кешировались
между попытками. Лог `FilmstripMeasurement` содержал время первого кадра,
готовности, число кадров, HTTP-запросов и прочитанные body bytes через
OkHttp `EventListener.responseBodyEnd`.

Теперь `VideoFilmstripLiveTest` явно отделяет рабочий original-first provider
от экспериментального HLS-first provider внутри теста. Он проверяет отсутствие
HLS discovery для читаемого original. Отвергнутый порядок HLS → original
сохранён только в opt-in benchmark для воспроизведения сравнения и AAC fallback.
Ниже приведены первоначальные измерения, а не новый прогон после смены политики.

Это оценка HTTP payload, а не счётчик интерфейса: TCP/TLS, заголовки и байты,
оставшиеся в сетевых буферах после отмены, не включены. `Content-Length`
не суммируется: для range extraction он завышает фактически прочитанный объём.
Дискового кеша приложения нет; кеши ОС/файловой системы сервера не очищались.
Холодным здесь называется именно транскодирование, не чтение исходного файла.

Среда: API 36 x86_64 emulator, Media3 1.11.0; `test.syrok`, Nextcloud 34.0.5,
Memories 11.1.4, go-vod 0.7.3, ffmpeg 7.1.5. Контейнер приложения ограничен
2 CPU / 1.5 GiB. Устройство и сервер находятся на одном хосте: это не замер
мобильной сети и не оценка расхода батареи телефона.

Файлы: синтетический H.264, 1920×1080, 30 fps, целевые 10 Mbit/s, GOP 60,
`faststart`; для успешного HLS сравнивались копии без аудио. Размеры исходников
15 990 917 / 75 989 195 / 226 004 556 bytes. Первый файл имел новый fileId;
для повторной проверки минутного файла использован новый VOD client id.
В server log подтверждены новые managers и запуск ffmpeg, а не выдача ранее
готовых сегментов. Probe cache минутного файла уже был тёплым — transcode нет.
Общие кеши и настройки стенда не менялись.

## Результат

МБ десятичные (1 МБ = 1 000 000 bytes); время — секунды.
Каждая строка — одно измерение, статистической оценки разброса нет.

| Длина / кадры | Трафик original → HLS, МБ | Первый кадр original → HLS, с | Вся лента original → HLS, с | Запросы original → HLS |
|---|---:|---:|---:|---:|
| 12 с / 7 | 27,24 → 1,17 | 2,55 → 7,66 | 11,56 → 11,02 | 8 → 16 |
| 60 с / 12 | 35,63 → 2,35 | 2,60 → 9,48 | 20,53 → 37,10 | 13 → 32 |
| 180 с / 15 | 45,46 → 3,14 | 1,13 → 9,74 | 24,44 → 85,25 | 16 → 40 |

Выбран настоящий фиксированный `480p.m3u8`; при успешных попытках обращений
к `/stream` не было. Трафик уменьшился в 14–23 раза. Готовность холодной ленты
на длинном ролике оказалась значительно медленнее: сервер последовательно
генерировал сегменты. До готовности всех кадров лента заполнялась постепенно.
Число HTTP-запросов выросло: повторные seek читают init и media segments.
12-секундная строка получена ещё с лимитом 5 с на кадр: он в этой попытке не
исчерпывался. Для 60/180 с действовали новые 15/90 с.
Даже маленький original может дать больше своего размера из-за повторного
чтения диапазонов; полного скачивания всего файла для каждого кадра нет.

На минутном ролике старый лимит 5 с прервал ожидание HLS после metadata:
получились fallback, 35,85 МБ и 28,71 с. Для проверки экспериментального HLS
бюджет увеличили до 15 с на кадр / 90 с на попытку; metadata — 8 с,
original — 5/45 с. Трёхминутный пример близок к общему лимиту.
Этот бюджет сохранён для редкого fallback после неподдерживаемого original;
при его исчерпании рабочая лента деградирует с retry, original повторно не читается.

## Ограничение fMP4 с AAC

На 12-секундном исходнике с обычным AAC encoder priming Media3 отклонил первый
fMP4-сегмент go-vod: `FragmentedMp4Extractor.parseTfdt`,
`IllegalStateException: Top bit not zero: -1024`. Копия того же видеопотока без
аудио прошла. Это подтверждённый пример несовместимости на стенде, а не вывод
о всех AAC-файлах или всех серверах Memories.

В экспериментальной политике HLS-first provider перешёл к original, завершил
ленту и не изменил playback. Рабочая политика теперь сразу использует читаемый
original и для этого файла не доходит до HLS.
В проверенном AAC-примере трафик original / HLS с fallback: 27,28 / 27,38 МБ,
первый кадр 1,07 / 8,10 с, вся лента 9,93 / 16,97 с. Экономии от HLS нет,
ожидание и трафик неудачной попытки добавляются к original. Исправление временных
меток go-vod или обход парсера Media3 в эту задачу не входят.

## Повторение

Opt-in test пропускается без `filmstripFileIds`. Нужны одноразовые файлы именно
на `http://test.syrok` под `test`; каждый новый замер HLS должен начинаться
с новым fileId или VOD client id, без playback того же клиента.

Передать runner arguments:

- `class=com.syrok0010.nextgallery.feature.viewer.VideoFilmstripLiveTest`;
- `filmstripServer=http://test.syrok`;
- `filmstripPassword` из локальной конфигурации стенда, не из Git;
- `filmstripFileIds` — fileIds через запятую;
- необязательный `filmstripFallbackIds` — подмножество с ожидаемым original
  fallback внутри экспериментального HLS-first provider, например отдельная
  фикстура с отрицательным tfdt.

Запускать `:app:connectedAutomationAndroidTest` в варианте `automation` по
[правилам тестирования](../agents/testing.md). Результаты — в logcat
`FilmstripMeasurement`. После проверки удалить одноразовую папку и только её
записи корзины. Постоянные fixtures не менять.

Готовые ленты дополнительно проверяются JVM-тестами LRU/revision/byte budget и
instrumentation: повторное раскрытие, смена качества проигрывания, удаление
Filmstrip из composition и восстановление не делают повторных frame-запросов.
Кеш находится в памяти viewer; повторное открытие viewer и process death не
сохраняют кадры. Локальная копия остаётся первым источником и не требует HLS.
