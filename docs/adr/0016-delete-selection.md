# ADR 0016: Удаление выбранных медиа в корзины

## Контекст

Режим выбора в таймлайне (ADR 0014, ADR 0015) умеет загружать и добавлять в альбом. Следующее базовое действие — удаление. У объекта может быть копия только на телефоне, только в облаке или обе (`LocalFirst`). Удаление необратимо для пользователя, если сделать его неосторожно. Поэтому важно, что именно удаляется и можно ли это восстановить.

Приложение не запрашивает права на запись медиа: minSdk 31, `MANAGE_MEDIA` и `MANAGE_EXTERNAL_STORAGE` нет. Чужие файлы MediaStore можно изменить только через системный запрос подтверждения.

## Решение

- В панели выбора появляется кнопка-иконка «Удалить». Она открывает диалог: сколько объектов только на телефоне, сколько только в облаке, сколько в обоих местах.
- Объекты с одной копией удаляются всегда. Для объектов с обеими копиями диалог спрашивает: «Везде» (по умолчанию), «Только с телефона», «Только из облака». Если таких объектов нет, вопроса нет.
- Телефонные копии попадают в корзину; возможность восстановления облачных зависит от сервера:
  - телефон — `MediaStore.createTrashRequest`; файл помечается `is_trashed` и исчезает из обычных запросов MediaStore, Android хранит его около 30 дней;
  - облако — `DELETE remote.php/dav/files/{uid}/{path}`; при включённом приложении Deleted files Nextcloud переносит файл в корзину пользователя.
- Если выбор затрагивает облачные копии, диалог при каждом открытии запрашивает `GET ocs/v2.php/cloud/capabilities?format=json` с авторизацией. Признак нигде не хранится: ответ свежий в момент решения, и не нужно сбрасывать его при смене сессии. Для `ocs/v2.php` неуспешный OCS-статус приходит не-2xx HTTP-кодом, поэтому `ocs.meta` не проверяется. Состояния:
  - ответа ещё нет — «Проверяем корзину Nextcloud…» со спиннером;
  - `files.undelete: true` — копии из облака попадут в корзину Nextcloud;
  - сервер ответил без `files.undelete: true` (`false` или поля нет) — предупреждение цветом ошибки: копии из облака удалятся навсегда;
  - ошибка запроса, не-2xx или ответ, который не разбирается в DTO, — предупреждение цветом ошибки: копии из облака останутся.
- Облачные копии удаляются, только если сервер ответил на запрос capabilities к моменту подтверждения. Кнопка «Удалить» не ждёт ответа: подтверждение до ответа или после ошибки удаляет только копии на телефоне, облачные остаются в ленте. Если удалить можно только облачные копии, а ответа нет, кнопка неактивна. Решение передаётся в `DeletionPreparation.confirm(scope, cloudAllowed)`, поэтому облачные цели не попадают в удаление независимо от текста диалога.
- Диалог показывает отдельные строки для телефонных и облачных копий выбранной области. Объекты только в облаке удаляются при любой области для объединённых объектов, поэтому облачная строка для них остаётся и при выборе «Только с телефона».
- Порядок: сначала системный диалог корзины телефона, затем облако. Системный диалог — последнее подтверждение. Если пользователь его отменил, не удаляется ничего, ни на телефоне, ни в облаке; выделение сохраняется. Если телефонных копий нет, облачное удаление начинается сразу после диалога приложения.
- Локальный индекс читает `MediaStore.Files`, а `createTrashRequest` принимает только URI коллекций изображений, видео и аудио. Поэтому `content://media/<volume>/file/<id>` переписывается в `.../images/media/<id>` или `.../video/media/<id>`.
- Путь на сервере берётся так же, как для альбомов (ADR 0015): `image/info/{fileId}` → `filename` и `etag`, uid — из сессии (`AccountCredentials.userId`, ADR 0006). `DELETE` отправляется с `If-Match: "<etag>"`: если между запросом пути и удалением файл переместили и по тому же пути оказался другой, сервер ответит `412`, и чужой файл не удалится. Без `etag` (старые версии Memories) защитой остаётся только свежий запрос пути. Не более 4 `DELETE` одновременно. `2xx` и `404` считаются удалением (файла уже нет — это и требовалось), `412` и остальные ответы — ошибкой этого файла; остальные файлы продолжают обрабатываться.
- Системный диалог возвращает `RESULT_OK`, даже если отдельные файлы не удалось переместить (MediaProvider не проверяет результат batch-операции). Поэтому после подтверждения каждая телефонная копия перечитывается с `QUERY_ARG_MATCH_TRASHED` и считается в корзине, только если `IS_TRASHED = 1`. Остальные попадают в итог как «не удалось переместить в корзину телефона».
- Экран передаёт в модуль удаления только `MediaId` выбранных объектов и выбранную область. Какие у объекта копии, модуль узнаёт сам из индекса медиатеки и фиксирует их до системного диалога: URI MediaStore и `fileId` Memories не выходят за пределы модуля, а то, что удаляется, не меняется, если индекс обновится, пока открыт диалог. Объекты, которые пропали из индекса после выбора, уже удалены и пропускаются.
- Android 16 отклоняет trash request больше чем на 2000 URI. Такой выбор не отправляется: приложение просит удалить меньше за один раз. Разбивать на несколько системных диалогов нельзя без пересмотра правила «отмена не удаляет ничего».
- Облачная часть выполняется в process-scoped корутине: телефонная часть к этому моменту уже подтверждена, итог должен пережить экран. Запросы выполняются по очереди. Пока итог не показан, результат следующей операции складывается с ним, а не заменяет его, поэтому ошибка ранней операции не теряется. Смена аккаунта отменяет всю очередь и сбрасывает результат.
- Выделение в сетке сохраняется через `rememberSaveable`: если Activity пересоздана, пока открыт системный диалог, после отказа выделение остаётся.
- После операции вызывается `MediaLibraryCoordinator.refresh()`. Удаление из MediaStore лента увидит и сама через observer, удаление на сервере — только после refresh. Ход облачной части («Удаление из облака: 3 из 8») и итог показываются в плашке статуса в шапке, удаляемые плитки ленты — индикатором (ADR 0018). Итог: сколько в корзине телефона, сколько удалено из облака, сколько не удалось удалить. Облачный итог не обещает корзину: DAV `DELETE` не подтверждает фактический способ хранения удалённого файла.

### Проверка доступности корзины на стенде

На `http://test.syrok/` (Nextcloud 34.0.5, Memories 10.1.0) проверено переключение `occ app:disable files_trashbin` / `occ app:enable files_trashbin`:

- с включённым приложением capabilities содержит `files.undelete: true`, `PROPFIND remote.php/dav/trashbin/test/trash/` с `Depth: 0` отвечает `207`;
- с выключенным приложением поле `files.undelete` отсутствует, тот же `PROPFIND` отвечает `404`;
- после включения признак и DAV-корзина восстанавливаются. Реальное удаление при выключенной корзине в этой проверке не выполнялось.

Для #127 выбран capabilities: проверенный признак доступен одним JSON-запросом и не требует DAV-пути с uid или разбора XML. Отсутствие поля считается отсутствием корзины: сервер доступен, удаление возможно, но восстановление не обещается.

## Критерии выбора

- Телефонные копии должны быть восстановимы; для облачных до подтверждения нужно честно показать зависимость восстановления от доступности корзины сервера.
- Пользователь до подтверждения видит, что и откуда удалится.
- Не требовать новых runtime-разрешений.
- Не удалять облачную копию, если пользователь отказался от удаления на телефоне в том же действии.

## Альтернативы

- **`createDeleteRequest` (удаление навсегда).** Тот же системный диалог, но без корзины. Отвергнуто: ошибочное удаление нельзя исправить.
- **Всегда удалять обе копии.** Проще, но смешивает разные намерения: освободить место на телефоне и убрать фото из облака. Пользователь выбрал вариант «спрашивать».
- **Сначала облако, потом телефон.** Тогда отмена системного диалога оставила бы объект удалённым только в облаке, хотя пользователь отменил действие.
- **Свой экран корзины в приложении.** Отложено: восстановление доступно в системной галерее (корзина Android) и в веб-интерфейсе Nextcloud.
- **Хранить признак корзины на время сессии** (запрос при входе и ручном обновлении медиатеки). Отвергнуто: требует сервиса с подпиской на сессию и сбросом при logout, а признак может устареть к моменту удаления. Запрос при открытии диалога проще и свежее; цена — один лёгкий запрос на диалог.
- **Блокировать «Удалить» до ответа сервера.** Отвергнуто: без сети пользователь ждал бы таймаута, хотя телефонные копии можно удалить сразу.
- **Удалять облачные копии и без ответа о корзине**, только предупредив. Отвергнуто: без ответа сервера удаление в облаке, скорее всего, не пройдёт, а если сеть вернётся между проверкой и `DELETE`, файлы удалятся без известной корзины.
- **Проверять корзину через DAV `PROPFIND`.** На стенде отличает включённое приложение от выключенного, но для текущего решения не даёт преимущества перед capabilities. Ответы об ошибке доступа всё равно не позволяют обещать корзину.

## Последствия

- Объекты с одной копией удаляются полностью; объединённые — по выбранной области. После «Только с телефона» объект остаётся в ленте как облачный, после «Только из облака» — как локальный.
- Если на сервере выключено приложение Deleted files, диалог предупреждает об удалении облачных копий навсегда (#127). Если сервер не ответил, облако не трогается. Признак — ответ на момент открытия диалога, а не атомарная гарантия: администратор может изменить конфигурацию, пока диалог открыт. Перед каждым `DELETE` отдельной проверки нет.
- Каждый облачный объект требует двух запросов (`image/info` и `DELETE`); телефонная копия — одного чтения MediaStore после подтверждения.
- Выделение хранится в saved state списком `MediaId`. Выбор из многих тысяч объектов приближает его к лимиту Binder-транзакции.
- Объекты с обеими копиями появляются после объединения. На Memories 10.1 эвристика `AUID`/`BUID` не срабатывает (issue #100). Поэтому на живой ленте выбор области доступен для файлов, загруженных из NextGallery и связанных по `OC-FileId` (ADR 0017), а для остальных — только при поддержке AUID/BUID сервером.
- Удаление доступно из viewer ленты. На экране открытого альбома и в его viewer действий пока нет (#133): удаление объекта из медиатеки нельзя смешивать с исключением из альбома.

## Действие из просмотрщика (#130)

Viewer ленты запускает тот же `SelectionAction` для одного текущего `MediaId`: подготовка копий в модуле удаления, `DeleteSelectionDialog` с областью для объединённого объекта и системное подтверждение корзины телефона. Отмена оставляет объект открытым. Удаление одной копии оставляет текущий `MediaId`, viewer получает оставшуюся копию из живой проекции.

При успешном удалении всех копий текущего объекта viewer после обновления проекции переходит к следующему объекту на его позиции, а для последнего — к предыдущему. Если целевой сосед ещё представлен плейсхолдером, viewer сохраняет текущую страницу, блокирует её действия и запрашивает диапазон вокруг позиции удаления в дне. После догрузки выбирается именно следующий/предыдущий слот, а не ближайший уже загруженный объект другого дня. Только пустая коллекция слотов подтверждает отсутствие соседей; тогда viewer закрывается без перехода к уже удалённому тайлу. При ошибке объект не удаляется из sequence принудительно.

Обычно viewer удерживает исчезнувший текущий объект при временных обновлениях. Модуль удаления отдельно хранит `MediaId` успешно завершённых полных удалений в пределах сессии: для них удержание выключено, когда они исчезают из живой проекции. Сигнал не зависит от потребления плашки результата и переживает пересоздание Activity; идентификаторы кандидатов сохраняются вместе с запросом системной корзины. Для смешанного массового выбора с ошибками сигнал не публикуется: результат модуля содержит общие счётчики, а не исход каждого объекта. Действие из viewer однообъектное и этого ограничения не имеет.

## Открытые вопросы

- Удаление из открытого альбома, включая его viewer, и судьба объекта, который входит в альбомы, обсуждаются в #133.
- Нужен ли собственный экран корзины с восстановлением?
