# ADR 0020: Восстановление действий после принятой загрузки

## Статус

Принято для #158 поверх упрощённого журнала PR #157. Уточняет ADR 0019,
0015 и 0017.

## Контекст

`UploadReceipt` уже означает принятую копию в облаке. Процесс может завершиться
между receipt и записью результата link или добавления в альбом. Повторять PUT
в этом случае нельзя: исходный URI может исчезнуть, а повтор создаст лишнюю
копию. Текущие Photos DAV возвращают `fileId` участника, поэтому членство можно
проверить отдельным `PROPFIND`, но сервер не даёт атомарной проверки и COPY.

## Критерии выбора

- receipt не меняется и не требует повторного чтения исходника;
- первый пользовательский COPY сохраняется;
- восстановление и явный retry повторяют link либо сверяют членство без COPY;
- отмена после receipt оставляет файл в облаке;
- решение использует один упрощённый `UploadJob`/`UploadAlbum`, без миграций,
  версий, requestId, owner token и generic-намерений.

## Решение

Журнал хранит `receipt`, состояния `linkStep` и `albumStep`, claim исполнителя
и pinned destination. `UploadQueue.retry(id)` переводит только Attention-шаги
задания с receipt обратно в `Pending`; transfer state и receipt не меняются.

После нового receipt текущий проход выполняет link и может один раз выполнить
COPY в выбранный альбом (`AlbumStepMode.Initial`). Если процесс остановился после
начала COPY, журнал переводит шаг в Attention. Восстановление и явный retry
используют `AlbumStepMode.Reconcile`: `PROPFIND Depth: 1` ищет точный `fileId`
в исходном альбоме. Найденное членство даёт Done; отсутствие или неоднозначный
ответ оставляет Attention. Второй COPY автоматически не выполняется.

Для link повторяется существующая операция с тем же `fileId` и текущей сессией.
Поздний ответ старого claim отбрасывается транзакционной проверкой revision и
executor. UI показывает «Повторить действие» только для follow-up после receipt;
отмена подавляет шаги и сохраняет загруженный файл.

## Альтернативы

- Повторять COPY после рестарта: 409 и существование альбома не доказывают
  членство нужного файла.
- Отменять весь job после сбоя follow-up: теряется подтверждённая загрузка и
  безопасный retry без PUT.
- Хранить отдельные v2 intents и миграцию: усложняет незапущенный продукт;
  typed `UploadAlbum` уже содержит нужную цель.

## Последствия

Обычный local→album сценарий делает один COPY. После process death пользователь
может подтвердить результат через retry без повторной загрузки. Если DAV не может
однозначно подтвердить membership, действие остаётся видимым и отменяемым.
Две Room DB не образуют общую транзакцию, а другой клиент всё ещё может изменить
альбом после успешной сверки.

## Открытые вопросы

- Для автоматического replay COPY нужен серверный атомарный контракт проверки
  album и fileId; до него повтор остаётся явным и read-only.
- Политика фоновых retry, WorkManager/UIDT и backoff относится к следующим
  срезам.
