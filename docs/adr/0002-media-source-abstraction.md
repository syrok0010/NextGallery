# ADR 0002: Абстракция источников медиа

## Статус

Принято.

## Контекст

Финальная идея проекта включает удаленные фото из Nextcloud/Memories, локальные фото на устройстве и синхронизацию между ними.

Первый MVP при этом должен быть проще: remote-first timeline без полноценной локальной синхронизации.

Есть риск написать первый UI напрямую под Memories responses и потом переписывать его при добавлении MediaStore или WebDAV fallback.

## Решение

Сразу ввести доменную абстракцию источника медиа:

```text
interface MediaSource
```

На старте реализовать:

```text
MemoriesMediaSource
```

Позже добавить:

```text
LocalMediaSource
NextcloudWebDavMediaSource
```

Repository должен отдавать приложению доменные модели:

```text
MediaItem
MediaDay
MediaTimeline
MediaAsset
```

Memories DTO, WebDAV XML/props и MediaStore cursor rows не должны попадать в UI.

## Начальная доменная модель

Минимальная модель для MVP-1:

```text
MediaItem
  id
  source
  remoteFileId
  displayName
  mimeType
  width
  height
  takenAt
  duration
  isVideo
  isFavorite
  etag

MediaDay
  dayId
  date
  count
```

Поля можно расширять только после появления реального API ответа и UI-сценария.

## Почему не использовать напрямую Memories `IPhoto`

`IPhoto` уже близок к нужной модели, но это контракт конкретного server app/web UI.

Если использовать его напрямую:

- UI станет зависеть от Memories;
- сложнее добавить local media;
- сложнее добавить WebDAV fallback;
- сложнее тестировать domain logic.

## Последствия

Плюсы:

- MVP остается простым, но не тупиковым.
- Можно развивать единый timeline.
- Можно отдельно тестировать mapping.

Минусы:

- На старте нужен mapping слой.
- Есть риск преждевременно раздуть доменную модель. Правило: добавлять только поля, которые нужны текущему сценарию или уже точно есть в API response.

## Идентичность в первом unified timeline

Локальная и облачная копии представляют один `MediaItem`, если совпал их `AUID` или `BUID`, вычисленный совместимо с Memories:

- `AUID = MD5(epoch + size)`;
- `BUID = MD5(basename + ImageUniqueID)`, а без EXIF `ImageUniqueID` — `MD5(basename + "size=" + size)`.

Выбрана совместимость с существующим алгоритмом Memories Android: он позволяет объединять уже имеющиеся локальные и облачные библиотеки без предварительной загрузки файлов целиком. Альтернативы — совпадение только по простым metadata или хеширование полного содержимого — соответственно дают больше ложных совпадений либо требуют недоступных в текущем API хешей и дорогого чтения файлов.

Это приблизительная идентичность, а не гарантия равенства содержимого: совпадение любого из двух идентификаторов может дать коллизию. В дальнейшем явная связь, записанная при upload/download, или хеш содержимого должны иметь приоритет над этой эвристикой.

Для объединённого `MediaItem` канонические метаданные и позиция в timeline берутся из Memories. Локальная копия при этом является предпочтительным источником thumbnail и оригинала, чтобы не использовать сеть; если облачной копии нет, и метаданные, и байты предоставляет MediaStore.

Если чтение предпочтительной локальной копии завершилось ошибкой, asset loader автоматически использует облачную копию того же медиаобъекта без смены `MediaId`. Без сети остается cached thumbnail или состояние ошибки открытия; объект не удаляется, пока cloud metadata подтверждают существование облачной копии.

Локальная дата нормализуется совместимо с Memories Android, включая вычисление `dayId = dateCache / 86400`. Это важнее самостоятельной «идеальной» timezone-модели в первом срезе: разные календарные границы local и remote источников могли бы поместить копии одного кадра в разные секции около полуночи.

`fileId` больше не является identity доменного объекта или UI. Каждый медиаобъект получает независимый `MediaId`; MediaStore ID/URI, Memories `fileId`, `AUID` и `BUID` хранятся как source-specific identifiers и ключи сопоставления копий. Navigation route, tile registry, viewer sequence, shared transitions и scroll anchors адресуются по `MediaId`.

При объединении уже опубликованного локального объекта с облачной копией сохраняется его текущий `MediaId`. Это позволяет обновить состав копий без пересоздания тайла или текущей viewer surface.

`MediaId` генерируется как непрозрачный идентификатор и сохраняется в Room вместе с привязками к source-specific identifiers. Он стабилен между обычными запусками приложения; потеря identity при разрешенном на текущем dev-этапе destructive reset базы допустима. `AUID`/`BUID` не используются как сам `MediaId`, потому что являются приблизительными, могут отсутствовать и могут конфликтовать.

`MediaItem` публикуется только после того, как identity registry восстановил существующий или
создал новый persistent `MediaId`; временные session-only идентификаторы не используются.

Если `AUID` и `BUID` новой копии указывают на разные существующие `MediaId`, автоматическое объединение не выполняется: копия получает отдельный медиаобъект, а конфликт сохраняется для диагностики. Хотя такой случай считается крайне маловероятным, автоматическое транзитивное слияние могло бы необратимо объединить разные пользовательские фото; нормальный путь остается простым — все найденные совпадения должны вести к одному `MediaId`.
