# ADR 0014: Ручная загрузка в облако: размещение и передача

## Статус

Принято. Персистентный журнал, WorkManager, повторы и шаги после загрузки описаны в [ADR 0019](0019-durable-manual-uploads.md).

## Контекст

Memories API предоставляет timeline и `timeline_path`, но не имеет endpoint для загрузки файлов; запись идёт через Nextcloud WebDAV. Нужны правила выбора папки назначения, безопасной обработки занятых имён без перезаписи и возобновляемой передачи больших видео без чтения файла целиком в память.

Nextcloud поддерживает chunked upload (`MKCOL remote.php/dav/uploads/{user}/{id}`, `PUT .../{n}` для частей `1…10000`, `MOVE .../.file`, `PROPFIND Depth: 1`, `Overwrite: F` → `412` и `OC-FileId` как у `PUT`; нетронутую загрузку сервер удаляет через сутки — `cache_chunk_gc_ttl`; на S3 `Destination` нужен на `MKCOL`, каждой части и `MOVE`, а части кроме последней — не меньше 5 МБ).

## Критерии выбора

- Большие видео не читаются целиком в память; после прерывания большого файла отправляются только недостающие части.
- Существующий файл никогда не перезаписывается; занятое другим файлом имя не теряет фото.
- Размер части chunked upload задаёт сервер (лимиты прокси, S3), без новых полей журнала и миграций.
- Модуль загрузки не зависит от модулей, которые им пользуются (`feature.upload` ↛ `feature.albums`).

## Альтернативы

- **Выбирать папку перед каждой загрузкой или добавить настройку сейчас:** лишний шаг в текущем сценарии; отдельная настройка «Папка загрузки» вынесена в #34.
- **Автоматический `MKCOL` для отсутствующей папки назначения:** требует политики создания вложенных каталогов и мог бы закрепить опечатку в настройке; выбрана явная ошибка (#117).
- **Считать занятое имя тем же файлом при совпавшем размере:** молча склеивает разные снимки с одинаковым именем и размером, а связь копий позволяет удалить «везде» чужой файл. Хеша содержимого у Nextcloud нет (`oc:checksums` есть, только если его прислал клиент).
- **Пропускать файл при занятом имени:** `IMG_0001.jpg` с разных устройств встречается часто, а пользователь явно запросил загрузку.
- **Фиксированный размер части в приложении или хранение id загрузки в журнале:** фиксированный размер может превысить лимит прокси администратора, а id задания в журнале уже уникален и стабилен.
- **Переиспользовать загруженные части для соседнего имени:** на S3 части привязаны к `Destination` первой загрузки; занятое во время передачи имя редко, поэтому загрузка начинается заново.
- **TUS / Range-PUT:** Nextcloud их не поддерживает.
- **Выполнять действия после загрузки внутри модуля загрузки:** связало бы `feature/upload` со всеми фичами-потребителями.

## Решение

### Граница вызова и назначение

- Вызывающая сторона передаёт в `UploadQueue.submit` только `MediaId` (аналогично удалению). Модуль загрузки сам находит локальные копии в `MediaLibraryIndex` и фиксирует их в задании: URI MediaStore не выходит за пределы модуля, а объекты с уже имеющейся облачной копией пропускаются. Связывание копий (ADR 0002) ищет объект по URI телефонной копии, а не по `MediaId` из выбора.
- Перед проходом очереди загрузка получает `timeline_path` из `GET /apps/memories/api/config`, делит по `;`, обрезает пробелы, отбрасывает пустые элементы и берёт первый путь (включая `/`). Без путей загрузка завершается ошибкой (#117).
- Файлы отправляются в `remote.php/dav/files/{uid}/{destination}/{name}`, где `uid` — `AccountCredentials.userId` (ADR 0006), а каждый сегмент пути кодируется отдельно.
- При отсутствии папки назначения (`404`/`409`) автоматический `MKCOL` не выполняется: возвращается ошибка с указанием проверить первую папку таймлайна в Nextcloud.

### Занятое имя и проверка байтов

- Перед передачей имя проверяется через `PROPFIND Depth: 0`, а запись идёт с `If-None-Match: *` (одиночный `PUT`) или `Overwrite: F` (`MOVE` при chunked upload) на случай гонки. Пробировать самим `PUT` дорого: веб-сервер принимает тело целиком до ответа `412`.
- Если имя занято, разный размер из `PROPFIND` сразу означает другой файл. При равном размере файл скачивается (`GET` с `If-Match` на ETag из того же `PROPFIND`) и побайтно сравнивается с локальным с остановкой на первом расхождении (`UploadPlacement.kt`).
- Совпавшие байты — файл считается уже имеющимся в облаке, а его `oc:fileid` связывает копии (ADR 0002). Другой файл размещается под соседним именем `name (2).ext`, `name (3).ext`… до `(100)` с той же проверкой; при исчерпании имён фиксируется конфликт имени.

### Одиночная и возобновляемая передача частями

- Размер части берётся из capability `files.chunked_upload.max_size` (по умолчанию 100 МиБ; `<= 0` отключает chunked upload), один запрос за проход. Частями идёт только файл больше одной части; меньшие файлы отправляются одним потоковым `PUT`.
- Имя chunked-загрузки — `id` задания из журнала (ADR 0019). Повтор читает список частей (`PROPFIND Depth: 1`) и досылает отсутствующие; при смене раскладки (другой `max_size` или номер части вне файла) загрузка удаляется и начинается заново.
- Потерянная сервером загрузка (`404` на часть/`MOVE`; на S3 `412` на часть при потере записи в Redis при оставшейся папке) удаляется и завершается временной ошибкой для повтора после backoff. `400` на `MOVE` (части не сходятся по размеру) требует внимания.
- `MOVE` с `Overwrite: F` при занятом имени удаляет временную загрузку (из-за привязки `Destination` на S3) и переходит к проверке байтов / соседнему имени.
- Отмена закрывает текущий DAV-вызов (включая чтение при сверке байтов) без отката сервера: если ответ сервера уже принят, файл остаётся в облаке и отменяются только шаги после загрузки.

### Действия после загрузки

Модуль загрузки отвечает только за доставку байтов. Последующие действия описываются в задании данными и выполняются шагами `UploadFollowUp` в модулях-владельцах (ADR 0019); `verifyFeatureBoundaries` запрещает `feature.upload` импортировать `feature.albums`.

## Последствия

- После индексации Memories облачная копия объединяется с локальной по `fileId` из `PUT`/`MOVE` или `PROPFIND` (ADR 0002).
- Побайтная сверка под занятым именем требует `GET` удалённого файла (для большого совпадающего видео — полного чтения).
- При прерывании chunked-передачи теряется не больше одной части; файлы до `max_size` идут одним `PUT` и при прерывании начинаются заново. Части отправляются последовательно (`max_parallel_count` не используется).
- Метаданные исходника проверяются до и после передачи (ADR 0019), но части прошлой попытки побайтно не перепроверяются: изменение файла без смены size, mtime и generation может дать смешанный файл. Отменённое задание оставляет временную загрузку на сервере до суточной очистки.

## Открытые вопросы

- Пользовательская настройка «Папка загрузки» вместо первого пути `timeline_path` (#34).
- Параллельная отправка частей chunked upload, если последовательная окажется медленной.
