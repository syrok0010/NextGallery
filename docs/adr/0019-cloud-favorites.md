# ADR 0019: Первый срез облачного избранного

## Статус

Принято для #129. Scope: кнопка текущего объекта в viewer ленты, альбома и папки,
а также фильтр ленты «Избранное в облаке». Массовое действие не входит в срез.

## Контекст

Медиаобъект может иметь локальную и облачную копию с разными признаками избранного.
Пользователь выбрал сначала облачное избранное. Обычный timeline загружает metadata
по viewport, поэтому фильтрация уже загруженных объектов потеряла бы старые фото.
Warm-start cache по ADR 0010 не обещает offline-полноту.

## Критерии выбора

- Один понятный источник истины для объединённого объекта.
- Старое облачное избранное находится без пролистывания всей медиатеки.
- Запись адресует проверенную облачную копию, а частичный DAV-успех не считается успехом.
- Подтверждённое изменение видно в коллекциях и сохраняется после перезапуска.
- Поздний ответ прежней сессии и начатый раньше refresh не отменяют изменение.
- Нет неявной загрузки локальных фото, системного диалога favorite или offline queue.

## Решение

Истина — Nextcloud `oc:favorite` облачной копии. У объединённого объекта значение
задаёт облако. `MediaStore.IS_FAVORITE` не читается и не изменяется. Local-only
viewer показывает неактивное сердечко и пояснение о доступности для фото в облаке.

Запись выполняется через DAV `PROPPATCH` после `image/info/{fileId}`. Проверяются
owner uid, fileId, путь и basename; `PROPFIND Depth: 0` сверяет fileId точного DAV
ресурса. `If-Match` защищает от замены файла между чтением и записью. Redirects
отключены и для lookup, и для DAV. Тело ответа читается и проверяется на IO
dispatcher: асинхронное получение заголовков само по себе не делает последующее
чтение body безопасным на Main. Успех — `207` с нужным свойством в успешном
`propstat` именно этого ресурса; ошибки, чужой href и XML entities отклоняются.
В первой версии запись в чужие облачные файлы не поддерживается.

Memories 10.1.0 поддерживает `GET days?fav=1` и `GET days/{ids}?fav=1`.
Индекс отфильтрован на сервере. Клиент использует preloaded details и последовательно
запрашивает все неполные дни порциями по десять. Здесь нет page token и нет
параметра `limit`: проверяется число уникальных fileId каждого дня. При изменении
состава во время чтения или неполном ответе показывается ошибка обновления,
а не обещание полной выборки. Состав фильтра и свойство различаются: отсутствие в этой выборке не снимает
сердечко у файла вне путей timeline, например доступного только через альбом.
Полнота относится к доступному индексированному
Memories timeline, не ко всем файлам Nextcloud, архиву или скрытым объектам.

Операция принадлежит application/session scope. Pending сохраняет прежнее значение
и показывает индикатор; повторные изменения блокируются до завершения. При ошибке
показывается сообщение, durable offline queue не создаётся. Сетевой запрос не
зависит от глобального флажка наличия интернета. Logout через UI блокируется
на время записи; generation дополнительно отбрасывает поздний результат даже
при повторном входе в тот же аккаунт.

Подтверждённые значения проецируются на общий индекс, viewer и содержимое альбомов.
Запись metadata и приём результатов чтения сериализованы: чтение, начатое до
подтверждения, не может вернуть прежнее значение ни в память, ни в Room. Новый
server refresh может принять изменение другого клиента. Выборка избранного
материализует metadata без объявления целого дня загруженным в обычном timeline.
Тот же приём с revision guard применяется к серверным ответам открытого альбома:
свежая отметка принимается даже для объекта вне timeline.
Сохранение из альбома обновляет только уже материализованные строки, включая
ранее подтверждённую отметку; само чтение альбома не добавляет его участников
в warm-start timeline. Ошибка сохранения прочитанных данных в warm-start cache
диагностируется, но не отменяет успешное серверное чтение; отмена coroutine
пробрасывается.
При invalidation дня сохраняются только записи, подтверждённые после начала
этого запроса. Более новый индекс может удалить устаревшую metadata, поэтому
подтверждение favorite не удерживает удалённое фото в кэше всю сессию.
При снятии сердечка в активном фильтре объект явно покидает viewer sequence:
выбирается сосед или закрывается пустая коллекция. Ключом остаётся MediaId.

## Альтернативы

- **Объединять Android и Nextcloud favorite через OR или изменять обе копии.**
  Требует политики конфликтов и системного подтверждения Android. Отложено вместе
  с локальным избранным; пользователь пока выбрал облачный срез.
- **Фильтровать materialized timeline.** Быстро, но выдаёт неполную выборку за всё
  избранное и пропускает старые дни.
- **Прочитать metadata всего timeline.** Проверяемо, но native `fav` позволяет
  получить только нужные дни и не обходить весь архив.
- **Оптимистично менять сердечко и откатывать.** Потребовало бы дополнительно
  согласовать исчезновение объекта из фильтра и rollback viewer position.
  Pending сохраняет объект до подтверждения и проще объясняет ошибку.
- **Полный refresh на каждый тап.** Лишняя сеть и окно гонок; достаточно
  подтверждённого изменения общей metadata и локальной проекции.

## Последствия и ограничения

- Offline доступна только сохранённая часть избранного с явной пометкой при ошибке
  обновления. Это не offline archive и не обещание наличия оригиналов.
- Большой избранный день по-прежнему читается одним ответом сервера; metadata всех
  избранных объектов хранится в памяти. Изображения загружает ленивый grid.
- При потере процесса во время незавершённой записи итог уточняется refresh;
  операция не восстанавливается и не повторяется автоматически.
- Избранное меняет свойства копии, не identity. Policy, миграции и reset #115,
  WorkManager и компромисс upload `412` (#131) не меняются.

## Открытые вопросы

- Как согласовывать локальное избранное с облаком в следующем срезе.
- Нужны ли batch actions и отдельная pagination для очень большого избранного дня.
- Когда вводить явное offline pinning и политику долговечности его metadata.
