# ADR 0020: Возобновление прерванной передачи частями

## Статус

Принято. Дополняет передачу ADR 0019: прерванная передача большого файла
продолжается с недостающих частей, а не начинается заново.

## Контекст

Передача из ADR 0019 — один `PUT`. Остановка worker, обрыв сети или смерть
процесса посреди большого видео теряют всё отправленное, а без foreground
системный лимит фоновой работы может не дать такому файлу дойти никогда.

Nextcloud поддерживает chunked upload (проверено на стенде, Nextcloud 34):
`MKCOL remote.php/dav/uploads/{user}/{id}` создаёт загрузку, `PUT .../{n}`
сохраняет часть `n` (1…10000), `MOVE .../.file` собирает части в файл и удаляет
загрузку. `PROPFIND Depth: 1` загрузки перечисляет сохранённые части с размерами.
`Overwrite: F` на `MOVE` отвечает `412`, если имя занято, а `OC-FileId`
возвращается, как у `PUT`. Загрузку, к которой не прикасались сутки
(`cache_chunk_gc_ttl`), сервер удаляет. На object storage (S3) части пишутся
сразу в цель multipart-загрузкой: там `Destination` нужен на `MKCOL`, каждой
части и `MOVE`, а части, кроме последней, — не меньше 5 МБ.

## Критерии выбора

- После прерывания отправляются только недостающие части.
- Сохраняются инварианты ADR 0014/0017/0019: проверка имени до отправки,
  создание без перезаписи, соседние имена, receipt, проверка исходника.
- Не нужны новые поля журнала и миграции.
- Размер части — решение администратора сервера (лимиты прокси, S3).

## Решение

Размер части — capability `files.chunked_upload.max_size` (системная настройка
сервера, по умолчанию 100 МиБ), один запрос за проход. Как и веб-клиент
Nextcloud, частями идёт только файл больше одной части; `max_size` ≤ 0
отключает их. Без capability берётся серверное значение по умолчанию.

Загрузка называется id задания, поэтому повтор находит её без записи в
журнал. Повтор читает список частей и досылает отсутствующие; части другого
размера (сменился `max_size`) или с номером вне файла означают другую раскладку —
загрузка удаляется и начинается заново. Потерянная сервером загрузка (`404` на
часть или `MOVE`; на S3 `412` на часть, когда Redis потерял её id, а папка
осталась) удаляется, и передача завершается временной ошибкой: следующая попытка
после backoff создаёт новую. Без удаления папки на S3 части отвергались бы до
суточной очистки. `400` на `MOVE` (части не сходятся по размеру) пропажей не
считается и требует внимания. `MOVE` с `Overwrite: F` заменяет `PUT` с `If-None-Match: *`: занятое
имя ведёт к сравнению и соседнему имени, как раньше, а загрузка удаляется —
части отправлялись для другого `Destination`. Прогресс считает уже сохранённые
части отправленными.

## Альтернативы

- **Фиксированный размер части в приложении.** Мельче шаг возобновления, но
  может превысить лимит запроса прокси, который администратор учёл в настройке.
- **id загрузки в журнале.** Лишнее поле: id задания уже уникален и стабилен.
- **Повторное использование частей для соседнего имени.** На локальном
  хранилище работает, на S3 части привязаны к `Destination` первой загрузки.
  Занятое во время передачи имя редко, поэтому файл отправляется заново.
- **TUS / Range-PUT.** Nextcloud их не поддерживает.

## Последствия

Прерывание теряет не больше одной части; при настройке по умолчанию файл до
100 МиБ по-прежнему идёт одним `PUT` и начинается заново. Метаданные исходника
проверяются до и после передачи (ADR 0019), но части прошлой попытки байтами не
сверяются: изменение файла без смены size, mtime и generation даст смешанный
файл. Отменённое задание оставляет загрузку на сервере до суточной очистки.
Повтор позже суток начинается заново. Части отправляются последовательно,
`max_parallel_count` не используется.

## Открытые вопросы

- Параллельная отправка частей, если последовательная окажется медленной.
