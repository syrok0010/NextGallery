# ADR 0017: Связь локальной и облачной копий после загрузки

## Контекст

После загрузки из таймлайна (ADR 0014) Memories индексирует новый файл. В ленте он появлялся отдельной облачной плиткой рядом с исходной локальной (#100). Объединение копий в `LocalFirst` держится на общем `MediaId`. Для облачной копии `MediaId` выдаёт identity registry, когда она впервые приходит в `days/{id}`, и сопоставляет её с локальной только по AUID/BUID.

Проверка на стенде показала, что Memories 10.1.0 не отдаёт `auid`/`buid` в `days/{id}`. Колонки `auid` в `oc_memories` нет вовсе. Эвристика поэтому не срабатывала ни для одного загруженного файла. Позже клиент стал вычислять AUID сам, но он приблизителен: расходится, если на одной стороне поменяли дату. Ошибку стоит считать блокирующей для загрузки: каждая загрузка порождает дубликат, а удаление (ADR 0016) не предлагает выбрать, где удалять, потому что копии не объединены.

Nextcloud возвращает в ответе на успешный WebDAV `PUT` заголовок `OC-FileId`, например `00000183ocmsigiy9k16`: `fileId`, дополненный нулями до восьми цифр, и instance id, который всегда начинается с `oc`. Этот `fileId` совпадает с `fileid` в Memories. Момент загрузки — единственный, когда обе идентичности известны вместе и без эвристик.

## Решение

- Сервис загрузки читает `OC-FileId` из ответа `201`/`204` на `PUT` и передаёт его в `UploadedFile.fileId`. Связывает копии действие после загрузки (ADR 0014) через `UploadedCopiesFollowUp`: запись `(MemoriesFile, fileId)` получает `MediaId` записи `(LocalContent, contentUri)` загруженного файла.
- Это действие `UploadQueue` добавляет в каждую партию. Связывание нужно любой загрузке, а не только той, что запросил конкретный экран, поэтому вызывающая сторона не должна о нём помнить.
- Связь хранится в той же таблице `media_identifiers`, что и остальные идентичности. Метод `MediaIdentityRegistry.link(existing, linked)` в одной транзакции находит `MediaId` известной копии и делает upsert записи новой копии на этот `MediaId`. Конфликт для этой записи снимается.
- Точная связь важнее эвристики. Если сервер уже успел получить свой `MediaId` (лента обновилась между `PUT` и связыванием) и других копий у того объекта нет, на общий `MediaId` переносятся и его aliases. Иначе следующий `resolve` вернул бы облачную копию к старому объекту по AUID/BUID.
- Связь не заменяется. Если у локального объекта уже есть облачная копия, новый `fileId` не перепривязывается к нему, а существующая связь сохраняется. Это защищает identity registry от ошибочного повторного upload или повторного follow-up. Объект, который успел проиндексироваться только как серверная копия до follow-up, по-прежнему объединяется с локальным объектом.
- Связь записывается, только если сессия, начавшая загрузку, всё ещё активна. Проверка выполняется в той же транзакции. Выход из аккаунта очищает идентичности Memories (`removeSource`) тоже транзакцией, а сессия к этому моменту уже сброшена. Поэтому загрузка, завершившаяся после выхода, не оставит старый `fileId`: на другом сервере тот же номер принадлежит другому файлу.
- Последующие `resolve` находят `fileId` в registry и возвращают общий `MediaId`. Проекция медиатеки объединяет копии в `LocalFirst` без изменений. Кэш таймлайна читает `MediaId` из identity storage. На Memories 10.1 офлайн-кэш пока отбрасывает облачные элементы без AUID/BUID (#109), поэтому без сети объединённый объект показывается как телефонный.
- При `412` сервис сохраняет проверку размера через `HEAD` (ADR 0014). Совпавшие имя и размер считаются достаточным основанием связать копии (#131, решение автора проекта): сервис запрашивает `oc:fileid` и `DAV:getcontentlength` через `PROPFIND Depth: 0` того же DAV-пути и передаёт ID в тот же follow-up, с `created = false`. ID принимается, только если размер в том же успешном `propstat` снова совпадает с локальным: между `HEAD` и `PROPFIND` другой клиент мог заменить файл. При несовпавшем, отсутствующем или некорректном размере файл остаётся подтверждённым по прежнему `HEAD`, но без связи (`fileId = null`). При другом или неизвестном размере в `HEAD` связывание не начинается.
- Проверено 31.10.2026 на стенде Nextcloud 34.0.5 / Memories 10.1.0: `HEAD` возвращает `Content-Length`, но не `OC-FileId`; `PROPFIND` с `oc:fileid` возвращает `207` и числовой ID в успешном `propstat` (`200`). Поэтому после совпадения размера используется `PROPFIND`, а не заголовок `HEAD`. Ошибка запроса, неуспешный `propstat`, отсутствующий или некорректный ID оставляют файл успешно подтверждённым по размеру, но без связи.
- После партии, в которой хотя бы один файл оказался на сервере, действие обновляет медиатеку. Так облачная копия появляется без ручного refresh. Feature-срез не зависит от `app`: обновление передаётся колбэком через DI, как в удалении.
- Ошибка связывания не делает загрузку неудачной: файл уже на сервере, хуже станет только отображение.

## Критерии выбора

- Связь по известному `fileId` должна иметь приоритет над AUID/BUID. Для `412` принимается риск одинакового имени и размера при разном содержимом: это согласованная эвристика, без проверки хеша. Неверное объединение может затронуть удаление «везде».
- Она не должна зависеть от версии Memories и её индексатора.
- Успешный `PUT` не требует дополнительных запросов; дополнительный `PROPFIND` нужен только после `412` с подтверждённым размером.
- Не менять модель проекции и правила `reconcileMediaIdentities` для остальных источников.

## Альтернативы

- **Ждать AUID/BUID от Memories.** Сервер 10.1 их не отдаёт, а BUID/AUID по определению приблизительны.
- **`PROPFIND oc:fileid` после `PUT`.** Даёт тот же `fileId`, но стоит лишний запрос, когда заголовок уже есть в ответе. Остаётся запасным вариантом, если какой-то сервер не пришлёт `OC-FileId`.
- **Оставлять `412` без связи.** При расходящихся датах AUID не объединит копии, хотя файл уже считается загруженным. Согласованный компромисс — связывать при совпадении размера, только в момент явной загрузки; общий поиск совпадений по имени не добавляется.
- **Связывать прямо в сервисе загрузки.** Так было в первой версии. Сервис снова знал бы, зачем загружается файл, а этого мы избегаем (ADR 0014).
- **Добавлять действие в каждом месте вызова.** Новый экран с загрузкой легко оставил бы дубликаты, если забыть это действие.
- **Хранить связь отдельной таблицей.** Это дублировало бы `media_identifiers`, а проекции и кэшу пришлось бы читать два источника.

## Последствия

Файл, загруженный из NextGallery, остаётся одной плиткой с локальной и облачной копиями. Это переживает перезапуск приложения, а удаление предлагает выбрать область. Файлы, загруженные другими клиентами или до этого исправления, объединяются по вычисленному AUID; при расходящихся датах остаются раздельными до явной загрузки из приложения, которая подтверждает размер и связывает существующий файл. Выход из аккаунта удаляет записи Memories из registry (`removeSource`), поэтому после повторного входа связь теряется.

## Открытые вопросы

Открытых вопросов нет:

- `412` с совпавшим размером связывается так же, как успешный `PUT`, через проверенный на стенде `PROPFIND oc:fileid` — #131.
- Файлы, загруженные раньше и не через NextGallery, отдельной сверки не требуют. Клиент сам вычисляет AUID облачной копии из `epoch` и `size`, как Memories, и объединяет копии с совпадающими датой и размером. На стенде после сброса данных приложения такие файлы снова показаны одной плиткой.
- Связи при выходе не сохраняются: выход очищает все данные приложения (#53).
