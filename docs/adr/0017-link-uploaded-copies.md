# ADR 0017: Связь локальной и облачной копий после загрузки

## Контекст

После загрузки из таймлайна (ADR 0014) Memories индексирует новый файл. В ленте он появлялся отдельной облачной плиткой рядом с исходной локальной (#100). Объединение копий в `LocalFirst` держится на общем `MediaId`. Для облачной копии `MediaId` выдаёт identity registry, когда она впервые приходит в `days/{id}`, и сопоставляет её с локальной только по AUID/BUID.

Проверка на стенде показала, что Memories 10.1.0 не отдаёт `auid`/`buid` в `days/{id}`. Колонки `auid` в `oc_memories` нет вовсе. Эвристика поэтому не срабатывает ни для одного загруженного файла. Ошибку стоит считать блокирующей для загрузки: каждая загрузка порождает дубликат, а удаление (ADR 0016) не предлагает выбрать, где удалять, потому что копии не объединены.

Nextcloud возвращает в ответе на успешный WebDAV `PUT` заголовок `OC-FileId`, например `00000183ocmsigiy9k16`: `fileId`, дополненный нулями до восьми цифр, и instance id, который всегда начинается с `oc`. Этот `fileId` совпадает с `fileid` в Memories. Момент загрузки — единственный, когда обе идентичности известны вместе и без эвристик.

## Решение

- Сервис загрузки читает `OC-FileId` из ответа `201`/`204` на `PUT` и передаёт его в `UploadedFile.fileId`. Связывает копии действие после загрузки (ADR 0014) из `UploadedCopies.followUp()`: запись `(MemoriesFile, fileId)` получает `MediaId` записи `(LocalContent, contentUri)` загруженного файла.
- Это действие `UploadQueue` добавляет в каждую партию. Связывание нужно любой загрузке, а не только той, что запросил конкретный экран, поэтому вызывающая сторона не должна о нём помнить.
- Связь хранится в той же таблице `media_identifiers`, что и остальные идентичности. Метод `MediaIdentityRegistry.link(existing, linked)` в одной транзакции находит `MediaId` известной копии и делает upsert записи новой копии на этот `MediaId`. Конфликт для этой записи снимается.
- Точная связь важнее эвристики. Если сервер уже успел получить свой `MediaId` (лента обновилась между `PUT` и связыванием) и других копий у того объекта нет, на общий `MediaId` переносятся и его aliases. Иначе следующий `resolve` вернул бы облачную копию к старому объекту по AUID/BUID.
- У объекта остаётся одна облачная копия. Повторная загрузка того же файла под другим именем переносит связь на новый файл, а прежний становится отдельным объектом. Две облачные копии с одним `MediaId` проекция таймлайна показала бы двумя одинаковыми плитками.
- Связь записывается, только если сессия, начавшая загрузку, всё ещё активна. Проверка выполняется в той же транзакции. Выход из аккаунта очищает идентичности Memories (`removeSource`) тоже транзакцией, а сессия к этому моменту уже сброшена. Поэтому загрузка, завершившаяся после выхода, не оставит старый `fileId`: на другом сервере тот же номер принадлежит другому файлу.
- Последующие `resolve` находят `fileId` в registry и возвращают общий `MediaId`. Проекция медиатеки объединяет копии в `LocalFirst` без изменений. Кэш таймлайна читает `MediaId` из identity storage. На Memories 10.1 офлайн-кэш пока отбрасывает облачные элементы без AUID/BUID (#109), поэтому без сети объединённый объект показывается как телефонный.
- Ответ `412` (файл с таким именем уже существовал) не связывается: это может быть другой файл с тем же именем.
- После партии, в которой хотя бы один файл оказался на сервере, действие обновляет медиатеку. Так облачная копия появляется без ручного refresh. Feature-срез не зависит от `app`: обновление передаётся колбэком через DI, как в удалении.
- Ошибка связывания не делает загрузку неудачной: файл уже на сервере, хуже станет только отображение.

## Критерии выбора

- Связь должна быть точной: неверное объединение позволит удалить «везде» не тот файл.
- Она не должна зависеть от версии Memories и её индексатора.
- Обойтись без лишних сетевых запросов на каждый файл.
- Не менять модель проекции и правила `reconcileMediaIdentities` для остальных источников.

## Альтернативы

- **Ждать AUID/BUID от Memories.** Сервер 10.1 их не отдаёт, а BUID/AUID по определению приблизительны.
- **`PROPFIND oc:fileid` после `PUT`.** Даёт тот же `fileId`, но стоит лишний запрос, когда заголовок уже есть в ответе. Остаётся запасным вариантом, если какой-то сервер не пришлёт `OC-FileId`.
- **Сопоставлять по имени и размеру при следующей загрузке ленты.** Это снова эвристика, она ложно срабатывает на файлах с одинаковыми именами.
- **Связывать прямо в сервисе загрузки.** Так было в первой версии. Сервис снова знал бы, зачем загружается файл, а этого мы избегаем (ADR 0014).
- **Добавлять действие в каждом месте вызова.** Новый экран с загрузкой легко оставил бы дубликаты, если забыть это действие.
- **Хранить связь отдельной таблицей.** Это дублировало бы `media_identifiers`, а проекции и кэшу пришлось бы читать два источника.

## Последствия

Файл, загруженный из NextGallery, остаётся одной плиткой с локальной и облачной копиями. Это переживает перезапуск приложения, а удаление предлагает выбрать область. Файлы, загруженные другими клиентами или до этого исправления, по-прежнему объединяются только эвристикой и на Memories 10.1 остаются раздельными. Выход из аккаунта удаляет записи Memories из registry (`removeSource`), поэтому после повторного входа связь теряется.

## Открытые вопросы

- Связывать ли `412` с совпавшим размером: сейчас это вероятно тот же файл, но доказательства нет.
- Как связать уже загруженные ранее файлы: пакетная сверка по имени, размеру и `datetaken` с явным подтверждением пользователя?
- Нужно ли сохранять связи при выходе из аккаунта, если вход выполнен в тот же аккаунт?
