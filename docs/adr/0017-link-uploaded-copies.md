# ADR 0017: Связь локальной и облачной копий после загрузки

## Контекст

После загрузки из таймлайна (ADR 0014) Memories индексирует новый файл. В ленте он появлялся отдельной облачной плиткой рядом с исходной локальной (#100). Объединение копий в `LocalFirst` держится на общем `MediaId`. Для облачной копии `MediaId` выдаёт identity registry, когда она впервые приходит в `days/{id}`, и сопоставляет её с локальной только по AUID/BUID.

Проверка на стенде показала, что Memories 10.1.0 не отдаёт `auid`/`buid` в `days/{id}`. Колонки `auid` в `oc_memories` нет вовсе. Эвристика поэтому не срабатывала ни для одного загруженного файла. Позже клиент стал вычислять AUID сам, но он приблизителен: расходится, если на одной стороне поменяли дату. Ошибку стоит считать блокирующей для загрузки: каждая загрузка порождает дубликат, а удаление (ADR 0016) не предлагает выбрать, где удалять, потому что копии не объединены.

Nextcloud возвращает в ответе на успешный WebDAV `PUT` заголовок `OC-FileId`, например `00000183ocmsigiy9k16`: `fileId`, дополненный нулями до восьми цифр, и instance id, который всегда начинается с `oc`. Этот `fileId` совпадает с `fileid` в Memories. Момент загрузки — единственный, когда обе идентичности известны вместе и без эвристик.

## Решение

- DAV-клиент читает `OC-FileId` из ответа `201`/`204` на `PUT`, загрузка передаёт его в `UploadedFile.fileId`. Связывает копии шаг после загрузки (ADR 0019) `UploadedCopiesFollowUp`: запись `(MemoriesFile, fileId)` получает `MediaId` записи `(LocalContent, contentUri)` загруженного файла.
- Шаг link журнал создаёт каждому заданию сам. Связывание нужно любой загрузке, а не только той, что запросил конкретный экран, поэтому вызывающая сторона не должна о нём помнить.
- Связь хранится в той же таблице `media_identifiers`, что и остальные идентичности. Метод `MediaIdentityRegistry.link(existing, linked)` в одной транзакции находит `MediaId` известной копии и делает upsert записи новой копии на этот `MediaId`. Конфликт для этой записи снимается.
- Точная связь важнее эвристики. Если сервер уже успел получить свой `MediaId` (лента обновилась между `PUT` и связыванием) и других копий у того объекта нет, на общий `MediaId` переносятся и его aliases. Иначе следующий `resolve` вернул бы облачную копию к старому объекту по AUID/BUID.
- Связь не заменяется. Если у локального объекта уже есть облачная копия, новый `fileId` не перепривязывается к нему, а существующая связь сохраняется. Это защищает identity registry от ошибочного повторного upload, а повтор шага после остановки (ADR 0019) безопасен. Объект, который успел проиндексироваться только как серверная копия до follow-up, по-прежнему объединяется с локальным объектом.
- Связь записывается, только если сессия, начавшая загрузку, всё ещё активна. Проверка выполняется в той же транзакции. Выход из аккаунта очищает идентичности Memories (`removeSource`) тоже транзакцией, а сессия к этому моменту уже сброшена. Поэтому загрузка, завершившаяся после выхода, не оставит старый `fileId`: на другом сервере тот же номер принадлежит другому файлу.
- Последующие `resolve` находят `fileId` в registry и возвращают общий `MediaId`. Проекция медиатеки объединяет копии в `LocalFirst` без изменений. Кэш таймлайна читает `MediaId` из identity storage. На Memories 10.1 офлайн-кэш пока отбрасывает облачные элементы без AUID/BUID (#109), поэтому без сети объединённый объект показывается как телефонный.
- Файл, который уже лежал под тем же именем, связывается, только если его байты совпали с локальными (ADR 0014). Его `fileId` берётся из `PROPFIND` вместе с ETag, а скачивание для сравнения закреплено на этом ETag: id принадлежит именно сравненному файлу. Такая связь так же точна, как после `PUT`, и не зависит от дат копий. На стенде Nextcloud 34.0.5 / Memories 10.1.0 `HEAD` не возвращает `OC-FileId`, а `PROPFIND` отдаёт `oc:fileid` в успешном `propstat`. Если id не пришёл, файл считается загруженным без связи.
- Тела WebDAV описаны `@Serializable`-моделями `xmlutil` поверх kotlinx.serialization (`core/network/dav/DavXml.kt`): из одной модели собирается запрос `PROPFIND` и разбирается `multistatus`. Объявлены только нужные элементы, остальные (`href`, чужие свойства) пропускаются. Значения читаются строками, потому что `propstat` со статусом 404 перечисляет запрошенные свойства пустыми элементами. Разбирает XML парсер `xmlutil` на чистом Kotlin, поэтому на Android и в JVM-тестах работает один и тот же код. Внешних сущностей этот парсер не загружает, а ответ с DOCTYPE клиент отклоняет явно. Версия закреплена на 0.91.3: 1.0.x собрана Kotlin 2.4, и компилятор 2.2 её не читает. После обновления Kotlin до 2.4 нужно перейти на 1.0, где удалены API, помеченные устаревшими в 0.91.
- После прохода очереди, в котором хотя бы один файл оказался на сервере, очередь обновляет медиатеку. Так облачная копия появляется без ручного refresh. Feature-срез не зависит от `app`: обновление передаётся колбэком через DI, как в удалении.
- Ошибка связывания не делает загрузку неудачной: файл уже на сервере, хуже станет только отображение.

## Критерии выбора

- Связь должна быть точной: неверное объединение позволит удалить «везде» не тот файл.
- Она не должна зависеть от версии Memories и её индексатора.
- Обойтись без лишних сетевых запросов на каждый файл.
- Не менять модель проекции и правила `reconcileMediaIdentities` для остальных источников.

## Альтернативы

- **Ждать AUID/BUID от Memories.** Сервер 10.1 их не отдаёт, а BUID/AUID по определению приблизительны.
- **`PROPFIND oc:fileid` после `PUT`.** Даёт тот же `fileId`, но стоит лишний запрос, когда заголовок уже есть в ответе. Остаётся запасным вариантом, если какой-то сервер не пришлёт `OC-FileId`.
- **Сопоставлять по имени и размеру при следующей загрузке ленты.** Это снова эвристика, она ложно срабатывает на файлах с одинаковыми именами.
- **Связывать прямо в передаче файла.** Так было в первой версии. Передача снова знала бы, зачем загружается файл, а этого мы избегаем (ADR 0014).
- **Добавлять действие в каждом месте вызова.** Новый экран с загрузкой легко оставил бы дубликаты, если забыть это действие.
- **Разбирать XML вручную через DOM.** Так было в первой версии. Имена тегов и пространства имён дублировались строками в запросе и в разборе. JVM-тесты проверяли Xerces, а на Android работает другая реализация DOM.
- **dav4jvm (DAVx⁵).** Это полноценный WebDAV-клиент, но начиная с 3.0 он работает только через Ktor и потребовал бы второй HTTP-стек рядом с OkHttp. Мажорные версии с несовместимым API выходили каждые один-два месяца, сборки публикуются только через JitPack, а свойства Nextcloud вроде `oc:fileid` всё равно описываются вручную. Нам нужны точечные операции, а не синхронизация коллекций: файловый клиент — не-цель (vision).
- **Хранить связь отдельной таблицей.** Это дублировало бы `media_identifiers`, а проекции и кэшу пришлось бы читать два источника.

## Последствия

Файл, загруженный из NextGallery, остаётся одной плиткой с локальной и облачной копиями. Это переживает перезапуск приложения, а удаление предлагает выбрать область. Файлы, загруженные другими клиентами или до этого исправления, по-прежнему объединяются только эвристикой и на Memories 10.1 остаются раздельными. Выход из аккаунта удаляет записи Memories из registry (`removeSource`), поэтому после повторного входа связь теряется.

## Открытые вопросы

Открытых вопросов нет:

- Уже существующий файл с теми же байтами связывается так же, как созданный `PUT`, — #131. Совпадения только имени и размера для связи недостаточно.
- Файлы, загруженные раньше и не через NextGallery, отдельной сверки не требуют. Клиент сам вычисляет AUID облачной копии из `epoch` и `size`, как Memories, и объединяет копии с совпадающими датой и размером. На стенде после сброса данных приложения такие файлы снова показаны одной плиткой.
- Связи при выходе не сохраняются: выход очищает все данные приложения (#53).
