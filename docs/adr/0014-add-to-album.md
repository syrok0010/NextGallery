# ADR 0014: Добавление выбранных медиа в альбом

## Контекст

Режим выбора в таймлайне (ADR 0013) позволяет действовать над несколькими медиаобъектами. Следующее действие — собрать выбранное в серверный альбом. Альбомы Memories — это альбомы Nextcloud Photos. Каталог и содержимое читаются через Memories API, но endpoint для записи у Memories нет: Memories Web добавляет фото в альбом через Nextcloud DAV.

## Решение

- В панели выбора появляется кнопка-иконка «В альбом». Она открывает bottom sheet со своими альбомами Nextcloud и пунктом «Новый альбом».
- В альбом попадают только медиаобъекты с облачной копией (`remoteFileId`). Чисто локальные объекты пропускаются, их число показывается в шторке и в итоговом сообщении.
- Запись идёт через DAV, как в Memories Web:
  - `GET /apps/memories/api/image/info/{fileId}` даёт `filename` (путь в файлах пользователя) и `basename`;
  - `COPY remote.php/dav/files/{uid}/{filename}` → `remote.php/dav/photos/{uid}/albums/{album}/{basename}`;
  - новый альбом создаётся `MKCOL remote.php/dav/photos/{uid}/albums/{album}`.
- `409 Conflict` на `COPY` означает «уже в альбоме» и не считается ошибкой. `405` на `MKCOL` означает, что альбом уже существует. Остальные ответы считаются ошибкой конкретного объекта; остальные объекты продолжают обрабатываться.
- DAV-пользователь берётся из `GET /ocs/v2.php/cloud/user` (`ocs.data.id`), а не из login name сессии: Login Flow может вернуть e-mail или другой login, отличный от uid.
- В список попадают только альбомы, где владелец из `cluster_id` (`owner/name`) совпадает с uid. Shared-альбомы других пользователей в первой версии скрыты.
- Операция выполняется в process-scoped корутине сессии, не более 4 запросов `COPY` одновременно. После завершения каталог альбомов обновляется, итог показывается snackbar.
- Одновременно выполняется одна операция. Пока она идёт, шторка блокирует выбор альбома и объясняет причину, выделение сохраняется. Выход из аккаунта отменяет и незавершённые HTTP-запросы, а не только корутину. Итоговый snackbar подтверждается только после показа на видимом экране.

## Критерии выбора

- Использовать контракт, который уже проверен в Memories Web и на тестовом стенде, а не недокументированные write-эндпоинты.
- Не загружать файлы неявно: добавление в альбом — метаданная операция без передачи байтов.
- Не терять операцию при пересоздании экрана, но не переносить результат в другую сессию.
- Не показывать действие, которое заведомо закончится ошибкой прав.

## Альтернативы

- **Сначала загрузить локальные объекты, затем добавить их.** Удобнее для пользователя, но связывает альбомы с загрузкой из ADR 0013, у которой нет персистентной очереди и связи загруженного файла с `MediaId`. Это следующий шаг стека.
- **Foreground service, как для загрузки.** Избыточен: запросы короткие и не передают содержимое файлов.
- **Shared-альбомы.** Memories Web пишет в них по пути `photos/{uid}/sharedalbums/{name} ({owner})`, но права коллабораторов на запись не проверены.
- **Подписи и раскладка панели.** Текстовая кнопка «В альбом» рядом с «Загрузить» не помещалась на экране 1080 px при стандартном масштабе: «Загрузить» переносилась по буквам. Поэтому действие стало иконкой с accessibility-подписью, а счётчик показывает только число.

## Последствия

- Добавление работает для облачных и объединённых (`LocalFirst`) объектов в собственные альбомы.
- Каждый объект требует двух запросов (`image/info` и `COPY`). Для сотен объектов это заметно медленнее пакетного API, но пакетного API нет.
- Счётчики в каталоге зависят от индексации Memories: файл, ещё не проиндексированный Memories, может появиться в альбоме позже.

- Нужно ли добавление из viewer и из экрана открытого альбома?
