# ADR 0001: Целевая архитектура и вертикальные срезы

## Статус

Принято; объединяет первоначальные ADR 0001 и ADR 0008.

## Контекст

NextGallery объединяет несколько развивающихся пользовательских сценариев: авторизацию, timeline, viewer, управление медиатекой и будущую синхронизацию. Нужна целевая архитектура, к которой можно приближать код постепенно: она должна поддерживать современную Android-разработку, сохранять локальность изменений и изолировать Android/API детали, не превращаясь в набор обязательных слоёв и однооперационных классов.

## Критерии выбора

- Однонаправленный поток состояния и событий UI.
- Пользовательский сценарий можно понять и изменить end-to-end внутри одного среза.
- Доменные правила тестируются без Compose, Android runtime и сети.
- Интеграции с сервером, MediaStore и persistence не проникают в UI.
- Абстракции и Gradle modules вводятся ради самостоятельной политики или lifecycle, а не ради симметрии структуры.

## Альтернативы

### Группировка в первую очередь по техническим слоям

Единообразно раскладывает файлы по `screens`, `viewmodels`, `repositories` и `usecases`, но распределяет один пользовательский сценарий между удалёнными частями проекта.

### Формальная Clean Architecture для каждой операции

Даёт одинаковую цепочку зависимостей, но создаёт shallow interfaces и use cases, которые только делегируют вызов и не скрывают решения.

### Один общий UI coordinator

Упрощает начальную сборку приложения, но связывает состояния и lifecycle независимых сценариев.

## Решение

Использовать современный Android-стек с declarative UI и reactive state: Kotlin, Jetpack Compose, Coroutines/Flow, lifecycle-aware state holders, dependency injection и локальное persistence. Конкретные библиотеки выбираются профильными ADR и version catalog; замена Koin, Room или отдельного UI-компонента сама по себе не меняет этот архитектурный стиль.

Организовывать прикладной код вертикальными срезами по пользовательским сценариям. Срез end-to-end владеет своим UI, состоянием, orchestration, прикладными правилами и feature-specific data adapters. Внутреннее деление среза на `ui`, `domain` или `data` допустимо, но не обязательно и не должно выносить части сценария в глобальные технические каталоги только ради одинаковой структуры.

Общий `core` должен оставаться небольшим. В него попадают только устойчивый язык и механизмы, которыми действительно владеют несколько срезов: например media identity, session lifecycle, transport primitives или database infrastructure. Feature-specific repository, mapping и persistence policy остаются в срезе, даже если технически используют общий network или database mechanism.

Внутри приложения сохранять направленность зависимостей:

```text
UI -> state holder -> feature policy -> feature adapter -> platform or server
```

Это схема ответственности, а не требование создавать класс или package для каждого звена. Use case вводится, когда скрывает политику или координирует несколько зависимостей; отдельный Gradle module — когда даёт измеримую независимость сборки, тестирования или владения.

Возможный вид целевой структуры:

```text
app/                    — composition root и root navigation
feature/auth/           — UI, Login Flow и auth-specific adapter
feature/timeline/       — UI, timeline policy, projections и adapters
feature/viewer/         — UI, viewer sequence и transition policy
feature/upload/         — UI, upload policy, queue и server adapter
core/media/             — общий язык медиа и identity
core/session/           — single-account lifecycle
core/network/           — общие transport primitives
core/database/          — database mechanism без feature policy
```

Названия каталогов иллюстративны. Архитектурная граница определяется владением поведением и направлением зависимостей, а не совпадением с этим деревом. `app` собирает срезы, срезы могут зависеть от `core`, а `core` не зависит от срезов. Один срез не использует внутреннюю реализацию другого; межсценарное взаимодействие проходит через узкий явный контракт.

Текущий код находится в переходном состоянии: UI уже сгруппирован по сценариям, но значительная часть feature-specific поведения расположена в общих `data` и `domain` packages. Эта раскладка описывает исходную точку рефакторинга, а не целевой шаблон. Приближение к north star выполняется постепенно вместе с изменениями соответствующего сценария, без обязательного big-bang переноса.

## Последствия

- Изменения сценария должны в основном оставаться внутри его среза от UI до integration boundary.
- UI не работает напрямую с transport DTO, MediaStore cursor или форматом persistence.
- Локальное дублирование предпочтительнее преждевременного общего слоя; код переносится в `core` после появления устойчивой общей ответственности.
- Общий `core` требует дисциплины, иначе снова превратится в горизонтальный слой со feature-specific поведением.
- Текущие package boundaries будут меняться по мере рефакторинга; ADR фиксирует north star и критерии, а не план миграции.
- Архитектуру нельзя проверить только формой каталогов: важнее владение поведением и направление зависимостей.

## Открытые вопросы

- Какие срезы первыми оправдают отдельные Gradle modules временем сборки, изоляцией тестов или самостоятельным lifecycle?
- Какой минимальный контракт нужен для взаимодействия timeline, viewer, upload и albums без прямых зависимостей между их реализациями?
