# ADR 0015: Добавление выбранных медиа в альбом

## Контекст

Режим выбора в таймлайне (ADR 0014) позволяет действовать над несколькими медиаобъектами. Следующее действие — собрать выбранное в серверный альбом. Альбомы Memories — это альбомы Nextcloud Photos. Каталог и содержимое читаются через Memories API, но endpoint для записи у Memories нет: Memories Web добавляет фото в альбом через Nextcloud DAV.

## Решение

- В панели выбора появляется кнопка-иконка «В альбом». Она открывает bottom sheet со своими альбомами Nextcloud и пунктом «Новый альбом».
- Объекты с облачной копией (`remoteFileId`) добавляются в альбом сразу. Чисто локальные объекты загружаются в облако и добавляются после загрузки (см. «Локальные объекты» ниже); шторка показывает оба числа.
- Запись идёт через DAV, как в Memories Web:
  - `GET /apps/memories/api/image/info/{fileId}` даёт `filename` (путь в файлах пользователя) и `basename`;
  - `COPY remote.php/dav/files/{uid}/{filename}` → `remote.php/dav/photos/{uid}/albums/{album}/{basename}`;
  - новый альбом создаётся `MKCOL remote.php/dav/photos/{uid}/albums/{album}`.
- `409 Conflict` на `COPY` означает «уже в альбоме» и не считается ошибкой, если альбом существует. Тот же код DAV возвращает для отсутствующего альбома, поэтому при `409` альбом проверяется одним `PROPFIND`; если его нет, такие объекты считаются ошибкой. `405` на `MKCOL` означает, что альбом уже существует. Остальные ответы считаются ошибкой конкретного объекта; остальные объекты продолжают обрабатываться.
- DAV-пользователь — uid сессии (`AccountCredentials.userId`, ADR 0006), а не login name: Login Flow может вернуть e-mail или другой login, отличный от uid.
- В список попадают только альбомы, где владелец из `cluster_id` (`owner/name`) совпадает с uid. Shared-альбомы других пользователей в первой версии скрыты.
- Операция выполняется в process-scoped корутине сессии, не более 4 запросов `COPY` одновременно. После завершения каталог альбомов обновляется. Ход и итог показываются в плашке статуса в шапке, добавляемые плитки ленты — индикатором (ADR 0018).
- Одновременно выполняется одна операция. Пока она идёт, шторка блокирует выбор альбома и объясняет причину, выделение сохраняется. Пока операция идёт, выход из аккаунта недоступен (#102, ADR 0018). Защитный сброс при изменении сессии по-прежнему отменяет и незавершённые HTTP-запросы, а не только корутину. Итог сбрасывается только после показа на видимом экране (ADR 0018).

### Локальные объекты

- Загрузка идёт тем же foreground service, что и в ADR 0014. Сервис ничего не знает об альбомах: `AlbumAdditions` ставит в `UploadQueue` партию с действием `AlbumUploadFollowUp` (ADR 0014, «Партии и действия после загрузки»).
- Для каждого файла, который дошёл до сервера, действие делает `COPY` загруженного DAV-пути в альбом. Ждать индексации Memories и `fileId` не нужно: `COPY` работает по пути. Файл, имя которого на сервере занято другим файлом, до действия не доходит и в альбом не добавляется.
- Сервис не создаёт альбомы. Партия ставится в очередь только после того, как `AlbumAdditions` получил адрес альбома: для нового альбома — после `MKCOL`. Иначе `COPY` мог бы опередить создание альбома и получить `409`. Если альбом создать не удалось, загрузка не запускается.
- Итог по альбому («В «X»: N, не добавлено: M») показывается в итоговом уведомлении загрузки и в итоге загрузки в шапке приложения (ADR 0018); пока файлы идут, их плитки показывают загрузку, а не добавление в альбом. Файлы, не дошедшие до сервера, считаются недобавленными; итог уже обработанных файлов при остановке на ошибке сохраняется. После добавления действие обновляет каталог альбомов.
- Если проверка альбома после `409` сама не удалась, неподтверждённые конфликты считаются ошибками только этих файлов; уже добавленные файлы остаются в итоге.

## Критерии выбора

- Использовать контракт, который уже проверен в Memories Web и на тестовом стенде, а не недокументированные write-эндпоинты.
- Не загружать файлы неявно: шторка до выбора альбома говорит, сколько объектов будет загружено в облако.
- Не добавлять в альбом файл, который может оказаться другим фото с тем же именем.
- Не терять операцию при пересоздании экрана, но не переносить результат в другую сессию.
- Не показывать действие, которое заведомо закончится ошибкой прав.

## Альтернативы

- **Пропускать локальные объекты.** Так было в первой версии, но пользователь не видит в таймлайне, у какого фото есть облачная копия, и действие часто ничего не делало.
- **Добавлять загруженные файлы по `fileId` после индексации Memories.** Требует ждать индексации и связывать загруженный файл с `MediaId`; `COPY` по DAV-пути этого не требует.
- **Создавать альбом в сервисе загрузки.** Тогда `MKCOL` из репозитория и сервиса конкурируют, и репозиторий мог бы получить `405` и показать ложную ошибку «альбом уже существует».
- **Foreground service, как для загрузки.** Избыточен: запросы короткие и не передают содержимое файлов.
- **Shared-альбомы.** Memories Web пишет в них по пути `photos/{uid}/sharedalbums/{name} ({owner})`, но права коллабораторов на запись не проверены.
- **Подписи и раскладка панели.** Текстовая кнопка «В альбом» рядом с «Загрузить» не помещалась на экране 1080 px при стандартном масштабе: «Загрузить» переносилась по буквам. Поэтому действие стало иконкой с accessibility-подписью, а счётчик показывает только число.

## Последствия

- Добавление работает для облачных и объединённых (`LocalFirst`) объектов в собственные альбомы.
- Каждый объект требует двух запросов (`image/info` и `COPY`). Для сотен объектов это заметно медленнее пакетного API, но пакетного API нет.
- Счётчики в каталоге зависят от индексации Memories: файл, ещё не проиндексированный Memories, может появиться в альбоме позже.
- Загрузка не персистентна (ADR 0014): если процесс убит до конца загрузки, оставшиеся файлы не загрузятся и не попадут в альбом.
- Результат добавления загруженных файлов виден в уведомлении и в плашке статуса приложения, в том числе во viewer ленты (ADR 0018).

## Действие из просмотрщика (#130)

Viewer ленты передаёт снимок текущего объекта в то же действие `SelectionAction`, что панель выбора. Открывается та же `AddToAlbumSheet`: облачный и объединённый объекты добавляются по облачной копии, локальный — после явного согласия на загрузку в шторке. Перелистывание после запуска не меняет снимок запроса. Принятый запрос закрывает шторку и оставляет viewer открытым; отказ или отмена не меняют текущий объект. Ход и итог доступны в шапке самого viewer (ADR 0018).

Viewer открытого альбома использует те же действия, что его сетка, с ограничениями ниже.

## Действия открытого альбома (#133)

Контекст: участник серверного альбома — ссылка Photos на облачную копию, а не отдельный файл. Удаление ссылки, исходного файла и коллекции используют HTTP `DELETE`, но имеют разные адреса и последствия. Локальная папка не имеет независимого членства. Критерии выбора: сохранить эти различия для пользователя, не менять область удаления копий (ADR 0016), не предлагать непроверенные права и не терять результат при навигации.

Решение:

- В своём серверном альбоме главное действие выбора — «Убрать из альбома». Диалог явно говорит, что телефон, облако и другие альбомы сохраняются. «Добавить в другой альбом» и «Удалить» находятся в меню панели; последняя операция проходит отдельное подтверждение ADR 0016. Viewer предлагает те же три действия для текущего объекта.
- Исключение получает одним `PROPFIND Depth: 1` точные DAV href и `oc:fileid` участников, затем удаляет только выбранные дочерние ссылки `photos/{uid}/albums/{name}/{fileId}-{basename}`, максимум четырьмя запросами одновременно. Адреса проверяются на совпадение сервера, коллекции и `fileId`; исходный путь `files/` и сама коллекция недопустимы. Ошибка listing останавливает эту операцию, частичные ошибки удаления сохраняют успешный результат остальных объектов. Исчезнувший после listing href считается ошибкой: файл мог быть переименован.
- В локальной папке доступны добавление в серверный альбом (с прежним upload follow-up для локального объекта) и удаление копий. «Убрать» отсутствует: перенос файлов из папки не входит в эту задачу. Самостоятельная загрузка остаётся действием ленты, добавление в альбом уже объясняет необходимую загрузку.
- Чужой серверный альбом остаётся для просмотра. Проверенный контракт записи относится к своим коллекциям; owner из `cluster_id` не доказывает права пользователя на исходные чужие файлы. Клиент пока не реализует collaborator mutation API и per-file permission model, поэтому не показывает там выбор и изменяющие действия. Альбом назначения выбирается только среди своих, текущий альбом исключён.
- Исключение выполняется в scope сессии, блокирует logout до окончания и отдаёт прогресс/накопленный итог общей плашке ADR 0018. Потребление сообщения не является событием изменения состава.
- Каталог публикует сигнал перечитывания после добавления, upload follow-up, исключения и удаления копий. Открытая папка также наблюдает MediaStore. При повторной загрузке прежний состав сохраняется до успешного окончания всех страниц: ошибка/промежуточная пустая страница не доказывает исключение. После полного обновления исчезнувшие `MediaId` снимаются с выбора; viewer переходит к соседу на позиции текущего, при пустом составе закрывается. Эти события отделены от удаления объекта из медиатеки: облачная копия может уйти из альбома, а локальная остаться в ленте.

Альтернативы: удалять по имени из плитки проще, но Photos адресует ссылки с `fileId`, а имя может измениться; полный listing даёт актуальные адреса без запроса `image/info` на каждого выбранного. Считать любое временное отсутствие в потоке окончательным исключением дешевле по памяти, но закрывает viewer и теряет выбор во время refresh. Повторно использовать удаление файлов для исключения недопустимо: это уничтожает копию и затрагивает другие альбомы.

Последствия: metadata listing имеет стоимость O(размер альбома), операции не персистентны при убийстве процесса. Обновление большого уже открытого альбома требует дождаться всех страниц и временно держит прежний состав; исходный объект до этого доступен во viewer. Итого с ошибками не исчезает до просмотра. Сведения о числе других альбомов не запрашиваются на каждый объект; общее предупреждение об удалении облачной копии описано в ADR 0016.
