# ADR 0019: Журнал ручных загрузок и восстановление при открытии

Уточнение durable AddToAlbum: [ADR 0020](0020-upload-follow-up-reconciliation.md)
сохраняет первый пользовательский COPY; после сбоя/retry выполняет только
проверку membership с явным attention, если результат подтвердить нельзя.

## Статус

Принято для первого runtime-среза #156 поверх #152. Уточняет upload-контракт
ADR 0014/0017/0018 и исключает журнал из disposable cache policy ADR 0010.
Исследование #155 служит основанием анализа, а не перечнем принятых решений.

## Контекст

Очередь, отмена и callbacks в памяти процесса пропадают при его уничтожении.
Foreground service повышает приоритет процесса, но не гарантирует выполнение
между PUT и связыванием копий. Успешная отправка и добавление в альбом имеют
независимые результаты; повтор всего сценария может изменить сервер дважды.

## Критерии выбора

- Принятое намерение, отмена и receipt переживают процесс; отказ диска не является Accepted.
- Старый исполнитель и другая сессия не принимают поздний результат.
- Существующие экран, conditional PUT и equal-size 412 сохраняются.
- Нет новых hash/reset правил #115, spool, multi-account UI или обещания scheduler.
- Неоднозначный результат последующего действия остаётся виден и отменяем.

## Решение

Отдельная Room DB `upload-journal.db` без destructive fallback хранит задания,
стабильный requestId, владельца сессии, состояния передачи, receipt и версии
последующих намерений. При отсутствии migration открытие/постановка завершается
ошибкой. Cache DB может пересоздаваться независимо. Журнал исключён из backup
и device transfer: MediaStore URI относится к конкретному устройству.

Enqueue подтверждается только после транзакции. Повтор requestId возвращает
прежнюю партию, включая скрытую историю. Очистка завершённых скрывает историю,
сохраняя receipt и дедупликацию в пределах сессии. Cancel и accept сериализованы
Room writer transaction; revision/executor fencing отсекает старый claim.
Accepted receipt необратим. Явная отмена незавершённых последующих действий
сохраняет receipt и подавляет дальнейшее выполнение, без compensating DELETE.

При новом процессе незавершённая передача становится uncertain. Destination
фиксируется до PUT и при recovery не меняется из-за нового timeline_path.
Повтор использует тот же `If-None-Match: *`: #131 принимает известный равный
размер после 412, #94 оставляет другой/неизвестный размер конфликтом. Receipt
ведёт только к последующим шагам, без повторного PUT. Это не exactly-once.

Источником остаётся оригинальный URI без spool. URI чтения точного тома хранится
отдельно от aggregate identity URI индекса (семантика ae6ba58). Доступ и известные
size/mtime/generation проверяются заново. Недоступность или наблюдаемое изменение
требуют внимания. Metadata не доказывает равенство bytes и не исключает изменение
во время чтения; после чтения выполняется повторная проверка доступных metadata.

Последующие действия описаны versioned данными. Link повторяем и ограничен
владельцем сессии. Album intent хранит разрешённую цель; первичное выполнение
возможно, но после рестарта сохранённый pending/running album-step требует
внимания, даже если COPY ещё не начинался: без доказанного
контракта точного membership он требует внимания. UI сохраняет успех загрузки
и отдельно показывает проблему действия. Неизвестная версия требует внимания.

Owner token хранится вместе с защищённой сессией: переживает process death,
сменяется при logout/relogin, даже для того же DAV uid. Выход запрещён, пока есть
waiting/retry/needs-attention или pending follow-ups. Все они доступны явной
отмене; завершённая история выход не блокирует. Credentials после выхода не
сохраняются. Общая полная очистка по #53 остаётся отдельной задачей.

Первый executor — существующий foreground service; восстановление начинается
при следующем видимом открытии. Serial drain здесь — свойство переходного
executor, а не навсегда выбранная пользовательская политика. Настройки сети,
числа повторов и параллелизма, backoff, WM/UIDT и фоновый scheduler — следующие
срезы. Автоматические сетевые retry в этом срезе не добавлены; незавершённые
ошибки требуют внимания и допускают отмену/новый выбор. Остановка executor с
callback переводит незавершённую работу всего переданного сервису прохода в
attention, сохраняет receipt и очищает handoff-состояние. Это относится и к
остановке между партиями и не запускает цикл немедленных рестартов;
внезапная смерть процесса оставляет running для uncertain reconciliation.

Просмотр сводки отмечается независимо от завершения задания: attention остаётся
в истории и блокирует выход, но уже прочитанное сообщение не появляется снова
после reopen. Новое изменение результата, включая явную отмену, публикует новую
сводку.

## Альтернативы

- Общая cache DB: дешевле wiring, но destructive reset уничтожает намерения.
  Ужесточение всех cache migrations расширило бы этот срез.
- WorkRequest на файл без journal: не хранит атомарную отмену/receipt/намерения
  и не решает неопределённый PUT/альбомный эффект.
- Spool: сохраняет bytes независимо от URI, но требует disk budget и политики
  хранения больших видео. Пользователь выбрал оригинальные URI.
- Автоматический replay album COPY по одному 409: существование альбома не
  доказывает membership нужного fileId в том же альбоме; отложен в следующий срез.

## Последствия

Две Room DB не имеют общей транзакции: link может повториться после смерти
между identity write и step receipt. Повторяемый link и owner guard сохраняют
безопасность; это не межбазовый atomic commit. Файл может успеть появиться на
сервере при отмене/потере процесса; отмена не удаляет его. При потере исходника
сохранено намерение, а не оригинальные bytes. Системные kill, force-stop и Stop
в Task Manager не являются durable пользовательской отменой конкретного файла.

## Открытые вопросы

- Безопасный album membership replay и восстановление результата COPY — срез 2.
- Пользовательские настройки и scheduler, причины системной остановки, retry и
  квоты Android — следующие срезы; any-network/1/5 не приняты как defaults.
- Полная очистка приложения #53 не реализуется этим ADR.
