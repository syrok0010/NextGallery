# ADR 0019: Журнал ручных загрузок и выполнение через WorkManager

## Статус

Принято. Дополняет протокол передачи (ADR 0014) и связывание копий (ADR 0002); исключает журнал из disposable cache policy (ADR 0010).

## Контекст

Очередь и callbacks в памяти процесса пропадают при его уничтожении, а foreground service, запускаемый только из видимого приложения, не продолжает работу после смерти процесса и не повторяет её без повторного открытия. Кроме того, передача байтов, связывание копий и добавление в альбом имеют независимые результаты: повтор всего сценария может изменить сервер дважды.

## Критерии выбора

- Принятое задание, отмена и receipt переживают смерть процесса; отказ записи на диск не подтверждает постановку.
- Остановленный исполнитель не может записать поздний результат поверх нового.
- Работа продолжается без открытого приложения, временные сбои повторяются автоматически.
- Сохраняются conditional `PUT`/`MOVE` и побайтная проверка занятых имён (ADR 0014).
- Без локального spool больших видео и без multi-account усложнений.

## Альтернативы

- **Foreground service из видимого приложения:** не переживает смерть процесса и не повторяет работу в фоне.
- **Отдельный `WorkRequest` на файл (без журнала или поверх журнала):** без журнала нет атомарной отмены, receipt и шагов; поверх журнала дублирует очередь в двух источниках.
- **UIDT JobScheduler (API 34+):** добавляет второй путь исполнения поверх WorkManager; отложено.
- **Общая cache DB (`NextGalleryDatabase`):** её destructive reset уничтожал бы активные задания, а модель `feature/upload` пришлось бы вынести в `core`.
- **Локальный spool:** сохраняет байты при удалении оригинала, но требует disk budget и политики хранения больших видео.
- **`REPLACE` для work в backoff:** сбрасывал бы backoff собственного worker и при постоянных 5xx слал запросы без задержки.
- **Повторять `COPY` в альбом после сбоя без проверки:** `409` при существующем альбоме не доказывает членство именно нужного `fileId`.

## Решение

### Хранение (`upload-journal.db`)

- Отдельная Room DB `upload-journal.db` хранит по строке на файл (без концепции «партии»): URI чтения точного тома MediaStore отдельно от aggregate identity URI индекса, снимок metadata (size, mtime, generation), необязательный альбом, состояние передачи, закреплённое имя назначения, receipt и состояния шагов после загрузки.
- На раннем этапе допускается destructive fallback при изменении схемы (без миграций). Журнал исключён из Android backup и device transfer (MediaStore URI привязан к устройству).
- Постановка (`EnqueueResult.Accepted`) подтверждается только после коммита транзакции.

### Исполнение, claims и восстановление

- Журнал — единственный источник очереди; WorkManager только планирует один unique work `uploads` (`UploadWorker`) с ограничением `CONNECTED` (зарядка не требуется, expedited с откатом в обычный) и политикой `APPEND_OR_REPLACE`, чтобы не перезапускать уже идущую передачу.
- Work планируется при постановке, ручном повторе и старте процесса (если в журнале есть ожидающие задания — это закрывает окно смерти процесса между коммитом журнала и сохранением work). Отложенное по временному сбою задание новый work не планирует, полагаясь на backoff самого worker (цена: новый файл, добавленный во время backoff, ждёт его окончания).
- Worker запрашивает foreground (`dataSync`) с уведомлением о прогрессе; при отказе Android 12+ в фоне продолжает как обычный worker с системным лимитом времени.
- Проходы `drain` (включая очистку в `finally`) сериализованы через mutex в процессе: WorkManager может запустить следующий worker до завершения очистки остановленного. Каждый файл захватывается транзакционным claim (`executor` + `revision`), который проверяется при каждой записи результата, поэтому отменённый или освобождённый исполнитель не может записать поздний ответ.
- При старте прохода worker освобождает оставшиеся claims (умершего процесса или прерванного прохода): начатая передача становится uncertain и повторяется безопасно — `destination` (сегменты `DavFilePath`, не URL) закреплён до первой передачи, а повтор проверяет имена с побайтным сравнением и `If-None-Match: *` / `Overwrite: F` (ADR 0014). Receipt ведёт только к шагам без повторной передачи. Это не строгое exactly-once (например, если прерванный `PUT` лёг под соседнее имя, а исходное успело освободиться, #184).

### Источник, ошибки и отмена

- Оригинальный URI читается без spool; size, mtime и generation проверяются до и после чтения (недоступность или изменение переводят задание в «Требует внимания»; metadata не доказывает побайтную неизменность).
- **Временные сбои** (`IOException`, HTTP `408`, `423` — lock Nextcloud после прерванного `PUT`, `429`, `5xx` кроме `507`) переводят передачу в uncertain / оставляют шаг pending и завершают worker с `Result.retry()` (экспоненциальный backoff без лимита попыток). Непредвиденная ошибка worker также возвращает `Result.retry()`, чтобы не провалить добавленные после него запуски.
- **Постоянные сбои** (исходник недоступен/изменился, конфликт имени, `507` нет места, прочие `4xx`, отказ шага) требуют внимания пользователя.
- Отмена сначала пишется в журнал, затем отменяет корутину файла. После receipt отменяются только оставшиеся шаги; файл в облаке остаётся, compensating `DELETE` нет.

### Шаги после загрузки (`UploadFollowUp`)

- Receipt создаёт шаги задания: `link` (связь копий, ADR 0002) всегда и `album`, если выбран альбом (ADR 0015). Журнал хранит только общие состояния шагов (`Pending`, `Done`, `Attention`, `Suppressed`); логику выполняют реализации `UploadFollowUp` в модулях-владельцах (`UploadedCopiesFollowUp`, `AlbumUploadFollowUp`).
- После остановки незавершённый шаг повторяется с флагом `recovered = true`. `link` идемпотентен. Восстановленный `album` сначала проверяет наличие точного `fileId` в альбоме через `PROPFIND Depth: 1` Photos DAV и только при отсутствии делает `COPY` (`409` после отрицательной проверки требует внимания). Временные ошибки шага также уходят в `Result.retry()`.
- Шаг в состоянии `Attention` можно повторить вручную без повторной передачи байтов; успех самой загрузки при этом сохраняется.

### Выход из аккаунта

Пока в журнале есть незавершённая работа (включая `Attention`), выход заблокирован (ADR 0006). Выход стирает данные приложения вместе с журналом и запланированным work (ADR 0010), поэтому привязка заданий к аккаунту не нужна.

## Последствия

- `NextGalleryDatabase` и `upload-journal.db` не имеют общей транзакции: при смерти процесса между записью identity и шага `link` последний повторится, но его идемпотентность сохраняет корректность.
- Файл может успеть сохраниться на сервере при отмене или смерти процесса; отмена его не удаляет.
- При потере исходника на устройстве сохраняется намерение задания, а не байты.
- Обновление приложения со сменой схемы журнала сбрасывает незавершённые задания.
- Системные kill и force-stop не считаются пользовательской отменой.

## Открытые вопросы

- Пользовательские настройки сети и зарядки, автозагрузка.
- Освобождение места после загрузки (#179) как новый `UploadFollowUp`.
