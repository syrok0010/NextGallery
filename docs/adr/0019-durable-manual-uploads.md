# ADR 0019: Журнал ручных загрузок и восстановление при открытии

## Статус

Принято для первого runtime-среза #156. Уточняет upload-контракт ADR
0014/0017/0018 и исключает журнал из disposable cache policy ADR 0010.
Исследование #155 служит основанием анализа, а не перечнем принятых решений.

## Контекст

Очередь, отмена и callbacks в памяти процесса пропадают при его уничтожении.
Foreground service повышает приоритет процесса, но не гарантирует выполнение
между PUT и связыванием копий. Успешная отправка и добавление в альбом имеют
независимые результаты; повтор всего сценария может изменить сервер дважды.

## Критерии выбора

- Принятое задание, отмена и receipt переживают процесс; отказ диска не является Accepted.
- Старый исполнитель не принимает поздний результат.
- Существующие экран, conditional PUT и equal-size 412 сохраняются.
- Нет новых hash/reset правил #115, spool, multi-account UI или обещания scheduler.
- Неоднозначный результат последующего действия остаётся виден и отменяем.
- Минимум механизмов: у приложения один пользователь и нет выпущенных версий.

## Решение

### Хранение

Отдельная Room DB `upload-journal.db` хранит по строке на файл: выбранный URI
со снимком metadata, необязательный альбом (владелец и имя), состояние передачи,
закреплённое имя, receipt, состояния шагов link и album и причину проблемы.
Пока приложение не выпущено, изменение схемы сбрасывает журнал (destructive
fallback, без migrations): задания теряются только при обновлении приложения, а
не при смерти процесса. Cache DB пересоздаётся независимо. Журнал исключён из
backup и device transfer: MediaStore URI относится к конкретному устройству.

Enqueue подтверждается только после транзакции; иначе пользователь видит отказ.
Очистка завершённых скрывает строки, не удаляя их до выхода.

### Исполнение

Журнал — единственный источник очереди. Пока приложение видимо и в журнале есть
свободные задания, оно запускает foreground service; каждое новое задание
запускает его ещё раз, чтобы заканчивающий проход не оставил его до следующего
открытия. Сервис по одному забирает задания из журнала (claim с `executor` =
id процесса и `revision`) до тех пор, пока они есть. Каждая запись проверяет
claim в той же транзакции, поэтому отменённое или переданное другому процессу
задание не принимает поздний ответ.

Отмена сначала пишется в журнал, затем отменяет корутину файла. До receipt
отменяется передача; после receipt подавляются только оставшиеся шаги, файл
остаётся в облаке, compensating DELETE нет.

### Восстановление

Новый процесс освобождает claims прежних, остановка сервиса — свои. Начатая
передача становится uncertain и выполняется снова, link повторяется, начатый
COPY в альбом требует внимания. Автоматический повтор передачи безопасен:
destination (исходное имя в папке таймлайна) закрепляется до PUT и не меняется
из-за нового `timeline_path`. Повтор заново проходит имена от исходного: файл с
теми же байтами под исходным или соседним `name (2).ext` принимается без нового
PUT, иначе файл ложится под первое свободное имя через тот же
`If-None-Match: *` (ADR 0014). Конфликт остаётся, только если свободного имени
нет. Receipt ведёт только к последующим шагам, без повторного PUT. Это не
exactly-once.

Destination и receipt хранят путь от корня файлов пользователя (сегменты
`DavFilePath`), а не URL: URL собирает только `FilesDavClient` (ADR 0005).

### Источник

Источником остаётся оригинальный URI без spool. URI чтения точного тома хранится
отдельно от aggregate identity URI индекса (семантика ae6ba58). Size, mtime и
generation снимаются при постановке и проверяются до и после чтения.
Недоступность или наблюдаемое изменение требуют внимания. Metadata не доказывает
равенство bytes.

### Последующие шаги

Link повторяем. Альбом шаг помечает running до COPY: после рестарта pending-шаг
выполняется как обычно, а running требует внимания, потому что без доказанного
контракта membership исход начатого COPY неизвестен. Явный retry после receipt
переводит только follow-up в pending: link повторяется, album сверяет точный
`fileId` через PROPFIND и второй COPY не делает. UI сохраняет успех загрузки и
отдельно показывает проблему шага.

### Ошибки, сводка и выход

Ошибки передачи и шагов не повторяются автоматически: задание требует внимания,
его можно отменить и выбрать файл заново. Просмотр сводки отмечается отдельно от
завершения: прочитанное сообщение не появляется снова после reopen, новое
изменение результата, включая отмену, публикует новую сводку.

Выход запрещён, пока есть незавершённая работа, включая требующую внимания; вся
она доступна явной отмене. Выход очищает журнал. Задания принадлежат
`server#uid`, а после выхода журнал пуст, поэтому новая сессия не видит и не
продолжает чужих заданий без отдельного owner token.

## Альтернативы

- Общая cache DB: дешевле wiring, но её сброс при каждом изменении cache-схемы
  уничтожал бы задания.
- WorkRequest на файл без журнала: не хранит атомарную отмену, receipt и шаги и
  не решает неопределённый PUT или эффект COPY.
- Spool: сохраняет bytes независимо от URI, но требует disk budget и политики
  хранения больших видео. Пользователь выбрал оригинальные URI.
- Передача партий в сервис из памяти (handoff): вторая копия очереди, которую
  надо сверять с журналом при каждой остановке. Сервис, читающий журнал, проще.
- Owner token сессии, requestId для дедупликации повторного enqueue и
  версионируемые generic-намерения: защищают совместимость и чужие сессии, но
  журнал сбрасывается при смене схемы и очищается при выходе, так что защищать
  нечего. Альбом хранится типизированным полем.
- Автоматический replay album COPY по одному 409: существование альбома не
  доказывает membership нужного fileId; отложен в следующий срез.

## Последствия

Две Room DB не имеют общей транзакции: link может повториться после смерти
между identity write и step receipt; повторяемость link сохраняет безопасность.
Файл может успеть появиться на сервере при отмене или потере процесса; отмена
его не удаляет. При потере исходника сохранено задание, а не bytes. Системные
kill, force-stop и Stop в Task Manager не являются пользовательской отменой.
Обновление приложения со сменой схемы теряет незавершённые задания.

## Открытые вопросы

- Серверный атомарный контракт для автоматического replay album COPY не найден;
  до него повтор остаётся явным и read-only (ADR 0020).
- Пользовательские настройки и scheduler, причины системной остановки, retry и
  квоты Android — следующие срезы; any-network/1/5 не приняты как defaults.
- Полная очистка приложения #53 не реализуется этим ADR.
