# Android-разработка для агента

Этот цикл применяется к изменениям Android-кода, UI и тестов на headless-хосте.
Устройство Docker-контура, сетевые ограничения и команды обслуживания описаны в
`dev/android/README.md`; сверяйся с ним, когда меняешь сам контур.

## Рабочий цикл

1. Перед изменениями прочитай затрагиваемый production-код и ближайшие тесты.
   Зафиксируй исходное состояние через `git status --short`. Шаг завершён, когда
   граница изменения и существующая проверка поведения найдены.

2. Веди tight loop на минимальной подходящей Gradle-задаче внутри `builder`:

   ```bash
   docker compose -f dev/android/compose.yaml run --rm builder \
     ./gradlew --no-daemon --console=plain <task>
   ```

   Для обычных JVM-тестов используй `:app:testAutomationUnitTest`; для сборки
   устанавливаемого APK — `:app:assembleAutomation`. Шаг завершён, когда
   затронутые тесты проходят и APK собирается, если изменение выполняется на
   Android runtime.

3. Для интерактивной проверки подними постоянный эмулятор:

   ```bash
   ./dev/android/run-dev.sh
   ./dev/android/adb.sh install -r \
     app/build/outputs/apk/automation/app-automation.apk
   ./dev/android/adb.sh shell am force-stop \
     com.syrok0010.nextgallery.automation
   ./dev/android/adb.sh shell am start -n \
     com.syrok0010.nextgallery.automation/com.syrok0010.nextgallery.MainActivity
   ```

   `emulator-dev` сохраняет приложения и userdata между запусками. Управляй им
   произвольными командами `./dev/android/adb.sh`: `shell input`, `uiautomator
   dump`, `screencap`, `logcat`, запуск Activity и чтение файлов. Шаг завершён,
   когда изменённый сценарий воспроизведён на экране и наблюдаемое состояние
   соответствует ожидаемому.

4. Собери доказательства по типу изменения. Для UI сохрани screenshot и при
   необходимости UI hierarchy; для падения или фоновой логики — релевантный
   logcat; для данных — проверь состояние через доступный API приложения или
   shell. Артефакты текущей задачи складывай в `build/android-dev/`, не добавляя
   их в git. Шаг завершён, когда результат можно проверить без пересказа хода
   работы.

5. Перед передачей изменения, влияющего на Android runtime, запусти чистый
   воспроизводимый прогон:

   ```bash
   ./dev/android/run-smoke.sh
   ```

   Smoke использует отдельный эмулятор с `-wipe-data`, собирает automation APK и
   сохраняет артефакты в `build/android-smoke/`. После него верни постоянную
   среду командой `./dev/android/run-dev.sh`, если работа продолжается. Шаг
   завершён только при успешном smoke и отсутствии неожиданного ANR в его
   артефактах.

6. В итоговом сообщении перечисли выполненные Gradle-задачи и runtime-сценарий,
   укажи пути к значимым артефактам и явно назови проверки, которые не удалось
   выполнить. Работа завершена, когда `git diff --check` проходит и каждый
   изменённый сценарий покрыт автоматической либо зафиксированной runtime-
   проверкой.

## Выбор устройства

- Контейнерный `emulator-dev` — основной инструмент разработки и исследования.
- `emulator-smoke` — чистая финальная проверка, а не рабочее userdata.
- Общее физическое устройство нужно для поведения, зависящего от реального
  железа, OEM или интеграций, которые эмулятор не воспроизводит. Перед таким
  запуском следуй `docs/agents/testing.md`, чтобы сохранить данные debug-приложения.

ADB опубликован без авторизации только на WireGuard-адресе `10.9.0.1:5555`.
Сохраняй эту границу при любых изменениях контура.
